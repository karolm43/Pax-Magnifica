## 23. Planet control when placing units (auto) — ✅ VERIFIED (AsyncTI4 bot)

📎 tirules: [Control](../../../../rules_tirules/R_control.md) · [Ground Forces](../../../../rules_tirules/R_ground_forces.md) · [Planets](../../../../rules_tirules/R_planets.md) · [Coexistence](../../../../rules_tirules/R_coexistence.md)

Placing/moving a GROUND FORCE or structure onto a planet automatically grants
control. Source (not from memory): AsyncTI4 `AddPlanetToPlayAreaService.addPlanetToPlayArea`,
called after EVERY unit change (`AddUnitService`/`RemoveUnitService`). Rule:

1. **Space does not count.** Changing units in the `space` zone (ships) does NOT change
   control of any planet (ships control only space — presence, RULES.md 19).
2. **Fighters are ignored.** When counting "who is on the planet", space units are skipped
   (in our code via the `is_space_unit` filter — a fighter is a space unit). Only infantry,
   mechs, space docks, and PDS (ground forces/structures) count.
3. **Exactly one color → control.** If after skipping fighters there is EXACTLY ONE player
   on the planet → grant control to them (overwriting the previous owner).
4. **Sticky control.** 0 players (empty planet) or ≥2 (coexistence) → control UNCHANGED.
   Removing the last infantry does NOT forfeit the planet — control persists until someone
   else takes it over (places their unit as the sole color). This is faithful to TI4.

Implementation: `board_edit.recompute_planet_control(system, planet)` called in `edit_units`,
`move_units` (source and destination zones), `set_planet_units` (when no explicit `owner_id`
is provided). An explicit `owner_id` from the operator takes priority (intentional God-Mode
override). Loss of control occurs only via takeover by another player or the explicit player
editor (`sync_controlled_planets`).

**Why this was a bug:** `edit_units`/`move_units` did not touch `planet_owners`, so placing
infantry did not grant control (the "controlled planets" panel did not update). web-data
computes controlled planets exclusively from `planet_owners` — hence no effect.
