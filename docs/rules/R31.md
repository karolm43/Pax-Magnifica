## 31. Action phase flow validation + active player (strict enforcement) — ✅ VERIFIED (LRR 2.0)

Milestone E8-T4. Source: local LRR 2.0 — `docs/rules_tirules/R_active_player.md`,
`R_action_phase.md`, `R_initiative_order.md`, `R_status_phase.md`, `R_agenda_phase.md`
(content © FFG; see SOURCE.md). First element of the "referee" (RULES.md 29.1): normal flow
actions are validated STRICTLY; God-Mode bypasses.

### 31.1. Active player per LRR vs DESIGN DECISION — ⚠️ DEPARTURE FROM SOURCE (see 31.4)

- Source rule (R_active_player): "The active player is the player taking a turn during the
  action phase." And explicitly in notes: "During the strategy, status and agenda phases, no
  player is the active player."
- **Design decision (2026-11, agreed with user — CORRECTS earlier T4 intent, see 31.4):** the
  engine INTENTIONALLY departs from "no active player". In an ONGOING game (≥2 players),
  `active_player_id` is ALWAYS set — including in STRATEGY, STATUS, and AGENDA — never `None`.
  Reason: the UI and AI bot always need an indicated player, and end of turn/phase should be a
  TRANSITION (announced by the speaker), not a "nobody's turn" state. `None` remains LEGAL
  exclusively as "game not started / <2 players / God-Mode building the table".
- Step order in STATUS/AGENDA is still a QUEUE by initiative/speaker order (31.3); the "active
  player" in those phases is only a POINTER to "whose turn it is now", it does not alter the rules.

### 31.2. Action phase flow validation — ✅ VERIFIED

Rules (R_action_phase, R_active_player):
- Players take turns in INITIATIVE ORDER (lowest card number first — RULES.md 9).
- Only the current ACTIVE player ends/passes their turn — not any arbitrary player.
- After passing, a player has no further turns (skipped until the end of the action phase).
- **A player CANNOT pass until they have performed the strategic action of their card** (playing
  the card = exhaust, RULES.md 30). (3-4 player variant: both cards — currently 1 card/player.)
- After everyone passes → status phase.

**Code enforcement (strict, `ValueError` → HTTP 422):**
- `end_turn(state, player_id=...)` / `pass_turn(state, player_id=...)`:
  - phase must be ACTION (otherwise error — in other phases there is no turn to end);
  - `player_id`, if provided, must equal `active_player_id` (not someone else's turn);
  - `pass_turn` additionally: player must have played their strategy card (`exhausted_strategy_cards`
    non-empty), otherwise "cannot pass before strategic action".
- Calling WITHOUT `player_id` (legacy/God-Mode-ish) behaves as before (for compatibility —
  however endpoints pass `player_id` from the request, so in practice they validate).
- **God-Mode** (`/god-mode/patch`, `board_edit`) bypasses — operator can set anything.

### 31.3. Order in STATUS/AGENDA = queue, not "turn" — ✅ VERIFIED

- **Status**: steps in INITIATIVE ORDER (R_status_phase). Scoring/actions per player in initiative order.
- **Agenda (voting)**: "starting with the player to the left of the speaker and continuing
  clockwise" (R_agenda_phase) — i.e. SPEAKER ORDER starting from the player after the speaker.
  This is the same mechanism as a timing window queue (RULES.md 29.2, `timing.build_response_queue`
  with initiator = speaker).
- **Conclusion for code:** when real status/agenda steps arrive (separate milestones), they will
  use a QUEUE (initiative or speaker order). `turn_flow` provides `initiative_order` (= `turn_order`)
  as the order for status. Since decision 31.4, `active_player_id` in STATUS/AGENDA points to
  the first player of that queue (not `None`), but resolving steps will still go through the
  queue — the "active" pointer does not alter the rules.

### 31.4. RULE "always someone's turn" + speaker announces transition — ⚠️ DESIGN DECISION (2026-11)

Agreed with user. Foundation for up to 6 human players (hot-seat / network) and AI bot: at any
moment in an ongoing game it must be clear WHOSE turn it is.

**(1) `active_player_id` never `None` in an ongoing game (≥2 players):**
- STRATEGY: active = current picker; once picks are complete = SPEAKER (waiting to announce).
- ACTION: active = player by initiative; once the last player passes = SPEAKER (phase still
  ACTION, no auto-advance — "end of turn"/"end of action phase" timing windows remain).
- STATUS/AGENDA: active = first player in initiative order (departure from LRR — 31.1).
- `None` ONLY outside gameplay: 0–1 players, empty setup, God-Mode building the table.
  `pick_count` does not support <2 players, so `next_strategy_picker` returns `None` there;
  code falls back to `speaker_id`, which can also be `None` in an empty game — and that is the
  only permitted `None`.

**(2) No auto-transition; phase transition is ANNOUNCED BY THE SPEAKER:**
- The last player passing / ending their turn does NOT switch the phase automatically — at the
  end of a turn and phase there are many timing windows that auto-transition would skip.
- Phase is changed via `/phase/next`, enforced as a speaker action: when the request provides
  `player_id`, it must equal `speaker_id` (otherwise HTTP 422). God-Mode (`/god-mode/patch`) bypasses.

**Code enforcement:**
- `turn_flow.end_turn`/`pass_turn`: when there is no next unpassed player → `active_player_id =
  speaker_id` (phase still ACTION), instead of `None`+STATUS.
- `turn_flow.next_phase`: ACTION → initiative[0]; STRATEGY → picker ∥ speaker; STATUS/AGENDA →
  initiative[0] ∥ speaker. `next_round`, `strategy_phase.pick_strategy_card`/
  `reset_strategy_cards`: picker ∥ speaker.
- `api/routers/flow.post_next_phase`: "must be speaker" validation (optional `player_id`).

**Implementation status:**
- ✅ "Always someone's turn" rule + speaker fallback across all flow/strategy functions.
- ✅ Speaker validation in `/phase/next`; end_turn/pass_turn validation (phase, active player,
  pass only after strategic action); God-Mode bypasses.
- ⬜ Real status steps (scoring, readying) — milestone E5, will use initiative order (queue).
- ⬜ Real agenda voting — milestone E6, will use speaker order (queue like timing window).

### 31.5. Pass as an action + single "finished phase" flag + "Next phase" gate — ⚠️ DESIGN DECISION (2026-11)

Agreed with user. Standardizes flow controls in the UI and corresponding semantics in the
engine, consistently across all phases.

**(1) Pass is "like an action", not ending the turn (ACTION phase):**
- `turn_flow.pass_turn` marks the active player `passed=True`, but does NOT hand over the turn —
  `active_player_id` stays unchanged. The turn is yielded with ONE consistent click of
  `end_turn` (also AFTER passing). Thus every turn ends the same way, regardless of whether it
  was a normal move or a pass. `end_turn` skips already passed players (`next_unpassed_player`).
- The "pass only after strategic action" gate (R_action_phase) is unchanged.

**(2) Single `passed` flag = "player finished their part of THIS phase":**
- `PlayerState.passed` is RESET on EVERY entry into a new phase (`turn_flow.next_phase`). It
  represents: pass in ACTION, step in STATUS (R31.3), reaction/vote in AGENDA.
- STATUS "Next player" and AGENDA "Pass" call `advance_active_player(mark_passed=True)`
  (`/turn/phase-step`) — mark the player and advance the pointer. AGENDA "Next player" calls
  `advance_active_player()` without marking (`/turn/next-player`) — only cycles.

**(3) "Next phase" (speaker) visible only once complete:**
- `turn_flow.can_advance_phase`: STRATEGY — after `ensure_strategy_complete`; ACTION/STATUS —
  when `all_passed` (everyone finished their part); AGENDA — always (subsequent votes are
  modeled with windows, not this gate).
- Projected to the UI via web-data fields `canAdvancePhase` + `allPassed`. Strict validation
  also in `api/routers/flow.post_next_phase` (clear 422 when speaker tries too early).

**(4) Notice panel (UI) = ONLY disallowed actions:**
- Separate box pinned at the TOP of the screen (`frontend/.../PhaseNoticePanel`). Shows
  EXCLUSIVELY messages about rejected actions (422 → `notice` in appStore): e.g., "Next phase"
  in strategy before everyone picks, "Pass" before playing a strategy card. Appears on event
  and DISAPPEARS WITH FADE-OUT (auto after ~6 s or close button). It is NOT a permanent reminder
  and does not announce phase changes. Replaces the old `NoticeBanner`.

**(5) "Next phase" always visible to the speaker; gate enforced via 422:**
- Instead of hiding the button until complete, the speaker ALWAYS sees "Next phase" in the
  main phases. When advancing is not allowed (strategy: not everyone picked; action/status: not
  everyone passed/stepped), clicking returns 422 with a clear message shown by the panel.
  Strict validation: `can_advance_phase` + `/phase/next`. Web-data fields
  `canAdvancePhase`/`allPassed` remain (diagnostics/bot).

**(6) Flow buttons call backend WITHOUT `player_id`:**
- The UI sends `/turn/pass`, `/turn/end`, `/turn/phase-step`, `/turn/next-player` without
  `player_id` — the backend targets its own `active_player_id`. Reason: the "desk player"
  (`useDeskPlayer`) sometimes falls back to the speaker and diverged from the real active
  player (status "Next player" sent the wrong id → 422 → "click did nothing").

**Code enforcement:**
- `turn_flow`: `pass_turn` (flag only), `end_turn` (sole turn handoff), `all_passed`,
  `can_advance_phase`, `advance_active_player(mark_passed=…)`, flag reset in `next_phase`.
- `api/routers/flow`: `/turn/pass`, `/turn/end`, `/turn/phase-step` (new), `/turn/next-player`,
  gate in `/phase/next`.
- `api/web_data`: fields `canAdvancePhase`, `allPassed`.
- Frontend: `TurnControls`, `GameStatePanel.PhaseControls` (per-phase buttons + gate),
  `PhaseNoticePanel` (+ `phaseNoticeMessage`), hook `useBoardEditor.phaseStep`.

### 31.6. End turn blocked while a timing window is active — ✅ VERIFIED (R_strategic_action) + ⚠️ UI DECISION (2026-11)

📎 tirules: [Strategic Action](../../../../rules_tirules/R_strategic_action.md)

Agreed with user. Ties strategy card secondaries (window 29.2) to ending a turn: the active
player who PLAYED a strategy card can click "End turn" ONLY after all other players have
decided on the secondary ("follow"/"don't follow").

**Source rule (R_strategic_action):** after the active player resolves the PRIMARY, each other
player — "beginning with the player to the left of the active player and proceeding clockwise" —
HAS AN OPPORTUNITY ("may resolve") at the secondary (following is optional). Only "after each
player has had an opportunity to resolve a strategy card's secondary ability" does the active
player exhaust the card and continue. Therefore: a turn cannot end "in the middle" of a window.

**Enforcement (referee):**
- `turn_flow.end_turn` raises `ValueError` when `state.pending_window is not None`
  ("Cannot end turn while a timing window is active…") → HTTP 422. The block applies to EVERY
  window type (secondary, hit assignment, space cannon, reaction), not only secondary — turns
  yield only "between" windows.
- The secondary window is opened by `strategic_action.play_strategy_card` (queue from player
  after active, clockwise — `timing.build_response_queue`), and each respondent answers via
  `/strategy/secondary` (`execute=True` = follow, `execute=False` = don't follow). After the
  last player answers, the queue completes and the window closes automatically
  (`resolve_secondary`). Only then does `end_turn` succeed.
- God-Mode (`/god-mode/patch`) bypasses here too — operator can close/clear the window manually.

**UI (boardgame terminology + popup):**
- Secondary decision labeled "Follow" / "Don't follow" (common TI4 tabletop term: "follow the
  strategy card"). In the engine it is still `execute` true/false.
- The prompt to the current respondent shows a MODAL (popup) in the center of the screen —
  `SecondaryDecisionModal` — rather than just a sidebar panel. The modal targets the respondent
  by `currentResponderId`; after a decision the queue moves to the next player (new modal).
- "End turn" (both places: `TurnControls` and `GameStatePanel.PhaseControls`) is DIMMED and
  disabled while `pendingWindow` ≠ null, with an explanatory tooltip (waiting for everyone to
  decide on secondary). Strict validation still lives in `end_turn` (422).
- SCOPE: the modal only provides the Follow / Don't follow CHOICE and advances the queue — WHAT
  exactly "follow" does (numeric effect of the secondary) is outside the scope of this step
  (effect dispatch in `strategic_action` will be added card by card, see RULES.md 30).

### 31.7. End turn requires an ACTION or a PASS — ✅ VERIFIED (R_action_phase)

📎 tirules: [Action Phase](../../../../rules_tirules/R_action_phase.md)

Agreed with user. A player cannot yield their turn "for nothing": on their action phase turn
they must perform ONE action or pass, and only then yield the turn.

**Source rule (R_action_phase):** "During a player's turn, they perform a **single action**" —
one of three: strategic, tactical, or component action. "If a player cannot perform an action,
they must pass." Thus turn = action XOR pass; there is no "empty" turn.

**Model (`PlayerState.took_action_this_turn`):** flag "player performed an action in the CURRENT
turn". Set to `True` by:
- strategic action — `strategic_action.play_strategy_card` (PLAYING A STRATEGY CARD counts as an action);
- tactical action — `tactical.activate_system` (activating a system starts the action);
- (component action — when its endpoint is added, it will set the same flag).
RESET on every turn handoff (`end_turn` clears it for the next player) and on entering the
action phase (`next_phase`) — because it applies to a SINGLE turn, not the whole phase.

**Enforcement (referee):**
- `turn_flow.end_turn` raises `ValueError` ("You must take an action … or pass before ending
  your turn.") → HTTP 422, when the active player has NEITHER `took_action_this_turn` NOR `passed`.
- `turn_flow.pass_turn` raises `ValueError` ("You already took an action this turn - end your
  turn instead of passing.") when the player already took an action THIS turn. Passing is an
  ALTERNATIVE to an action on a given turn, not an addition after it (R_action_phase: "perform
  a single action … or pass"). So after playing a card / activating a system, the only exit is `end_turn`.
- Passing (`pass_turn`) is a separate, allowed path to end the turn (RULES.md 31.5): after
  passing, End turn succeeds despite no "action" (passing IS ending activity for the round).
- EMPTY secondary window: when the respondent queue is empty (solo game / no other players),
  `strategic_action.play_strategy_card` does NOT open a window — otherwise `pending_window`
  would stay set (a "finished" window with nobody to close it) and permanently block End turn.
- God-Mode bypasses (operator can yield the turn manually).

**UI (web-data + panels):** `playerData[].tookActionThisTurn` carries the flag to the frontend.
"End turn" is enabled only when `tookActionThisTurn || passed` and no window is active; before
that it is GRAY (disabled) with hint "Take an action or pass, then End turn." After an
action/pass, the button pulses (nudge) + a small note that the turn still needs to be ended.
The "Pass" button is DISABLED when the player already took an action this turn
(`tookActionThisTurn`) — with tooltip "You already acted this turn — End turn instead".

### 31.8. Component action — third type of action phase action — ✅ VERIFIED (R_component_action)

📎 tirules: [Component Action](../../../../rules_tirules/R_component_action.md) · [Action Phase](../../../../rules_tirules/R_action_phase.md)

**Source rule (R_component_action):** a component action is a type of action performed on a
player's turn during the action phase. It is marked with an "**Action**" header on a component —
action card, technology, leader, relic, exploration card, promissory note, or faction sheet.
"To perform a component action, a player reads the action's text and follows the instructions."
A component action CANNOT be performed if its effect cannot be fully resolved; if canceled, it
does NOT consume the player's action. An action card WITHOUT an "Action" header is not a
component action (R_action_cards). It is one of the three turn actions (RULES.md 31.7): action =
strategic XOR tactical XOR component, or pass.

**Model (`core/component_action.play_component_action`):** PURE function `state -> state`.
SCOPE (intentional skeleton, "make it exist first"): records that the player performed a
component action this turn (`took_action_this_turn = True`, like strategic/tactical action) —
and nothing else. The effect of the SPECIFIC component is NOT executed; it will arrive via
dispatch on `component_id`, component by component, with a separate rule entry/source. For now
`component_id` is solely an ANNOTATION of "what was played" (goes into the event label),
optional — because an action can also come from a relic/tech/ability, not just a card.

**Enforcement (referee):** `play_component_action` raises `ValueError` → HTTP 422 when: phase ≠
ACTION; no active player; `player_id` ≠ active player; an open window is active
(`pending_window`); player already acted this turn (`took_action_this_turn` — one action per
turn); player has passed (`passed` — after passing, no more actions this phase, R_action_phase).
On success, `End turn` becomes available (same path as after strategic/tactical action). Endpoint:
`POST /tactical/component-action` (`ComponentActionRequest{player_id?, component_id?}`).

**UI (`TurnControls`):** in the action phase, next to Pass/End turn, a "**Component action**"
button (spark icon, purple ability accent). Clicking opens a "what did you play?" modal listing
ALL components with an "Action" header available to the active player — gathered from data,
without hardcoding (`componentActions.collectComponentActions`): action cards in hand (`window`
"Action"), faction abilities (`getAbilityKind === "action"`), leaders (`abilityWindow`/
`abilityText` starting with "ACTION"), technologies and relics (`text` with "ACTION" header).
The list reads what the player ACTUALLY owns (web-data `playerData[]`:
`abilities`/`leaderIDs`/`techs`/`relics` + hand). At the end there is always a "Something else"
option (exploration / promissory / untracked source). The choice is only an annotation
(`component_id`); effect = marking the action taken. Button DISABLED when the player already
acted / passed / a window is active (consistent with Pass).

### 31.9. End turn vs ongoing tactical action — ✅ VERIFIED (R_tactical_action, R_action_phase)

📎 tirules: [Tactical Action](../../../../rules_tirules/R_tactical_action.md) · [Action Phase](../../../../rules_tirules/R_action_phase.md)

**Source rule:** a tactical action ends after the production step; a player's turn ends after
performing an action. There is no "turn yielded while tactical action is still ongoing" state —
the next player starts their turn without someone else's active system, combat, or invasion.

**Model (audit 2026-11-11, `turn_flow.end_turn`):** when `tactical_step` ≠ None, End turn CLOSES
the tactical action via the same path as the "End action" button (`tactical.end_action`):
- blocks (`ValueError` → 422): ongoing combat (`active_combat` not DONE), unfinished invasion,
  open Space Cannon / reaction window, mandatory space combat (two players with ships in the
  active system, step ≤ SPACE_COMBAT), ongoing exploration;
- detected capacity excess (RULES.md 39.6) / fleet pool excess (RULES.md 42) or "after tactical
  action" reactions (e.g., Dark Energy Tap) OPEN a window and the turn STAYS with the player —
  they resolve the window and click End turn again (history label `turn:end-blocked`);
- a clean action (e.g., after movement without combat) ends and the turn moves on; the activation
  token stays on the board.
Router `/turn/end` passes `registry` (capacity check). Previously, End turn during combat left
someone else's `active_system` / `active_combat` for the next player (BUG).
