### 43.1. Rules (apply to every exception implementation)

1. **The base rule knows no exceptions.** In `core/`, it is forbidden to write `if faction == ...`, `if card_id == ...`,
   or conditions for a specific card/agenda/technology. The base rule invokes a HOOK POINT,
   and the exception is registered separately in `core/rules_hooks.py`.
2. **Exception = registration, not editing the rule.** Adding a card/faction = a new registry entry
   (component source → hook point → function) + entry in RULES.md + test. Zero changes to the base rule,
   unless a hook point is missing (then we add a point, not a workaround).
3. **Hooks are pure functions** (`state, context -> result/state`), with no I/O or HTTP, deterministic
   (randomness only via the engine's seedable RNG). A hook does not mutate its input (clone like the rest of `core/`).
4. **Hook point types (categories):**
   - `MODIFY` — alters a number/flag during calculation (movement, roll, cost, limit, range, production value);
   - `PERMIT/FORBID` — expands or narrows action legality (validation → `ValueError` → 422);
   - `TRIGGER` — reaction to an engine event, opens a timing WINDOW (when/after/before/instead of);
   - `REPLACE` — "instead of": swaps step resolution (explicitly, with precedence);
   - `PERSISTENT` — lasting effect (agenda law, persistent card), with expiration (end of phase/round/game).
5. **Ordering and conflicts are explicit.** Multiple hooks on one point ⇒ deterministic order:
   REPLACE first, then FORBID, PERMIT, MODIFY (additive before multiplicative), finally TRIGGER.
   Ties: initiative order / clockwise from active player (like windows, RULES.md 29.2).
   Rule "forbid beats permit" (can't > can) — to be verified on tirules2 at first conflict.
6. **Timing windows for reactions.** Every TRIGGER hook operates through `core/timing.py` (player queue),
   never via its own path. Trigger classification = `timing_spec.py` (RULES.md 34).
7. **Missing hook ≠ error.** A component without an implementation is "inert" and marked in `effects_registry`
   (`NOT_IMPLEMENTED`); the engine does NOT guess, instead handing the decision to the operator (`MANUAL`, God-Mode)
   and clearly communicating it in the UI. Status `IMPLEMENTED` may only be set once there is a hook + RULES entry + test.
8. **Source of truth for text:** card/ability text from JSON assets; clarifications from tirules2.com
   (`docs/rules_tirules/`). Never from memory. Every hook has in RULES.md: component, text (or asset id),
   hook point, timing, source, status ✅/⚠.
9. **Data unchanged:** numerical values (units, costs, tech) still only via `StaticDataRegistry`;
   the hook modifies the result, never duplicates stats.
10. **Exceptions tested in pairs:** test "without exception → base rule" and "with exception → altered result".
    Plus regression test: empty registry ⇒ behavior identical to before hooks were introduced.
11. **God-Mode bypasses hooks** just like rules (RULES.md 29) — it is a safety valve. A God-Mode event does not fire TRIGGERs.
12. **Thematic split instead of one huge file.** Hooks are grouped by topic (`hooks/factions_*.py`,
    `hooks/action_cards.py`, `hooks/agendas.py`), with registration in one place. File size is a soft
    guideline (typically up to ~500 lines for a cohesive module); thematic cohesion decides, not line count alone.

### 43.1a. Central Points: a hook attaches in one place (RULE)

- An operation that cards/abilities can affect (payment, gaining/losing a resource, tokens, exhausting,
  changing planet control, destroying/placing a unit, gaining technology, points, drawing a card)
  has ONE function in `core/`. Modifying the corresponding state field outside that function is forbidden
  (exception: God-Mode in `core/board_edit.py`).
- Why: we attach a hook once in the central function, not at every call site. Example: "spend commodities
  as trade goods" = one entry in payment sources, if all payments go through `pay(...)`.
- Guard: an architecture test scanning `src/core/` and detecting writes to those fields outside the central function
  (plan: PLAN_PELNA_ROZGRYWKA.md, block C8). Audit of scattered sites and function list: ibid.
- Temporarily (until end of H2): an exception needed before hooks is written in one named place with a
  `HOOK-CANDIDATE` comment (like `_PRODUCTION_FORBIDS`).

### 43.2. Rollout Order (Rationale)

1. **Mechanism first, content second.** `rules_hooks` skeleton + hook points in existing rules
   (movement, combat, production, status, windows), migrating the Arborec exception from `production.py` as the first
   test case. Reason: without the skeleton, each of ~30 faction exceptions and hundreds of cards would force editing base rules.
2. **Coverage report** based on `effects_registry` + `timing_spec`: how many components hit which hook
   point ⇒ priority = points serving the most components.
3. **Action cards** (uniform schema: timing + effect) — first large test of the skeleton.
4. **Factions**: simple ones first (number/legality modifiers), structure-breaking ones last
   (e.g., Nekro, Creuss, Mahact, Naalu, Yssaril, Titans, Cabal, Obsidian, Firmament).
5. **Agendas** last: require a working agenda phase (voting) and persistent laws (`PERSISTENT`).
6. The long tail of unhooked cards remains `MANUAL` (God-Mode) — a conscious trade-off, not hidden debt.

### 43.4. Player Reactions and the STOP Button (Interrupt Model) — ⚠ ASSUMPTION (design decision, to confirm)

This is a design principle (how the engine provides an opportunity to react), not a TI4 rule. It applies to cards and abilities
played "in reaction" (when / after / before / instead of — classification in `timing_spec.py`, RULES.md 34).
Goal: avoid asking every player after every action "do you play a card?" while NOT revealing
who holds it. Mirrors tabletop play: "stop, before that happens, I play a card".

**Game mode (user decision):** NETWORKED play (humans over network) + bots. Hot-seat is NOT supported,
so there is ONE reaction model for everyone (no split by mode). Bots run inside the engine, but
go through the exact same timing path as humans (see below: uniform cadence).

**Overarching principle: engine behavior visible to players CANNOT depend on hand contents.**
Any externally visible difference (prompting a specific player, instant confirmation "because nobody has it",
different pause duration) leaks information. Especially dangerous with UNIQUE cards (e.g., there is only one
Public Disgrace in the game): the prompt itself or its absence tells everyone who has it or that nobody does. Therefore we REJECT
the "pending pick + prompt only actual holders" variant (useful only with a single human).

**Model (applies as a whole):**
1. **The action step applies IMMEDIATELY (optimistically).** Nobody is asked, nobody gets a window, so
   the engine sends no hand-dependent signal.
2. **STOP is always available** to any human who could react based on PUBLIC information
   (filter below). The engine remembers the state before the last step. STOP restores that state, opens a timing
   window with the stopping player as the first respondent (the rest in window order, RULES.md 29.2),
   and after resolution resumes the interrupted action. STOP uses the same machinery as windows (`core/timing.py`).
3. **The STOP window lasts until the next COMMITTED action** (by any player). Server ordering decides:
   if the next action arrives before STOP, STOP loses (no rewinding more than one step).
4. **Uniform cadence (protective pause).** After every step to which some card could react, the next
   action (including a bot's) is held for a FIXED duration, the same for everyone and independent of hands (around 1–2 s,
   configurable). When the next actor is human, their own thinking time provides a "free" window.
   Bots holding a card play it via the same STOP path at the same cadence as humans (no
   instant bot reaction externally visible only when it has a card).
   **Implementation (2026-11-16, RULES.md 54.10–54.11):** in key windows and in the Sabotage window the duration is
   FIXED (set by host, default 4 s), the engine auto-passes for players without a matching card, and passes are private.
5. **Filter by PUBLIC information (the only allowed way to skip the pause).** The pause and STOP button may be
   skipped only when PUBLIC data proves nobody can react: e.g., all
   potentially reacting cards are already in the discard pile / spent, or no player has action cards in hand
   (action card count is public). The filter NEVER reads hand contents or hidden information, so its
   operation never reveals who holds a card.

**Example: Public Disgrace** ("When another player chooses a strategy card during the strategy phase:
that player must choose a different strategy card instead, if able"): the pick executes immediately; a player
with the card presses STOP during the pause window; the pick is reverted (strategy card choice is public and
deterministic, so reverting reveals nothing); a window opens with the stopper first; after
playing the card, the chooser MUST pick a different strategy card. Once played and discarded, the filter (item 5)
disables pauses on picks, because nobody can react anymore.

**Checkpoints and irreversibility boundary:**
- Every action step to which a card/ability can react is a CHECKPOINT
  (determined by `timing_spec`). STOP reverts strictly to the last checkpoint, not the entire action.
- STOP operates only up to the nearest IRREVERSIBLE point: dice roll, card reveal, drawing
  from a deck (hidden or random information). Beyond it, rewinding is blocked. Reason: prevents using knowledge
  from the future (seeing a roll result and only then pressing STOP). At the table this corresponds to "say before
  rolling". Natural UI point: the "Roll" button.
- Random outcomes are stored (seedable RNG, memory: dice on the engine side), so rewinding before
  a roll does not allow rerolling it.
- After playing a card via STOP, the interrupted step resumes from the same checkpoint, taking into account
  the card's effect (REPLACE/MODIFY hook, 43.1). If the card cancels the step ("instead of"), the step does not execute.

**Rewind mechanism (existing code):** `core/event_store.py` keeps a stack of state snapshots with `goto(seq)`
and `undo()`/`redo()`. The engine is built around `state -> state`, so "state before the step" already exists. What is new
is solely tagging snapshots as checkpoints/irreversible and blocking rewind past a
checkpoint. NOTE: regular operator Undo (God-Mode, history) is distinct from STOP and remains exempt from
these restrictions. Touches `event_store.py` / `state_service.py` (shared with the activity feed).
