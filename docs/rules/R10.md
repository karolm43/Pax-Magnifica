## 10. Owned Units and Upgrades (`unitsOwned`) — ✅ VERIFIED (data)

📎 tirules: [Unit Upgrades](../../../../rules_tirules/R_unit_upgrades.md) · [Units](../../../../rules_tirules/R_units.md) · [Technology](../../../../rules_tirules/R_technology.md) · [Units (components)](../../../../rules_tirules/C_units.md)

Source (not from memory): AsyncTI4 unit data (`assets/.../units/*.json`) + frontend
code `frontend/src/entities/lookup/units.ts` (`lookupUnit`, `preferUpgradedUnit`).
Verified 2026-10 on loaded registry (base+pok+codex).

**How the frontend resolves a unit for rendering and stats:**
- `playerData.unitsOwned` is the list of unit IDs owned by the player.
- `lookupUnit(asyncId, faction, playerData)` filters units with a given `asyncId`
  to those in `unitsOwned` and via `preferUpgradedUnit` selects the variant with
  `upgradesFromUnitId` (upgraded), when present. Stats (combat, move,
  capacity) and the upgrades panel read from the unit selected this way.

**Upgrade ↔ technology link (from data, verified):**
- Every generic upgraded unit has `upgradesFromUnitId` = base unit and
  `requiredTechId` = upgrade technology alias. Confirmed mapping:
  `carrier2→cv2`, `cruiser2→cr2`, `destroyer2→dd2`, `dreadnought2→dn2`,
  `fighter2→ff2`, `infantry2→inf2`, `pds2→pds2`, `spacedock2→sd2`.
- `warsun` (generic) has `requiredTechId="ws"` — owned only after researching
  the War Sun technology. Innate faction variants (e.g. `muaat_warsun`) have no
  `requiredTechId` and are owned from the start.

**`unitsOwned` emission rule (`web_data._units_owned_for_faction` implementation):**
For each `asyncId` we pick EXACTLY ONE unit (owning two with the same
asyncId breaks `lookupUnit`). Priority:
1. player's faction variant, upgraded (when they have the required technology),
2. player's faction variant, base,
3. generic variant, upgraded (when they have the required technology),
4. generic variant, base.
A tech-gated unit (with `requiredTechId`) that the player does NOT have is skipped.
Unit ownership by a faction: **the `FactionDef.units` list is authoritative** (plus
the unit's `faction` field as fallback). Keleres shares `keleres_flagship`/`keleres_mech`
across 3 variants, while the `faction` field only points to `keleresm` — without the `units` list, the other
two variants lost their flagship/mech. An upgrade inherits ownership from its base
(`upgradesFromUnitId` in the `units` list).

**Why this matters (Bug 11):** previously the serializer skipped ALL units with
`upgradesFromUnitId`, so after researching e.g. Carrier II the panel and map kept showing
base Carrier stats. Now researching an upgrade technology swaps the entry
in `unitsOwned` for the upgraded variant → `preferUpgradedUnit` displays the correct stats.
