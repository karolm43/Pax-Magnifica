## 28. Playable factions vs system placeholders (Neutral/Lazax) — ✅ VERIFIED (AsyncTI4 data)

📎 tirules: [Neutral Units](../../../../rules_tirules/R_neutral_units.md) · [⚪ The Firmament / ✖ The Obsidian](../../../../rules_tirules/F_firmament.md) · [Abilities](../../../../rules_tirules/R_abilities.md)

In AsyncTI4 faction data (`assets/data/factions/`), there are entries that are NOT playable
factions, only system placeholders for neutral units / scenarios:
- `neutral` (`other.json`, source `thunders_edge`) — empty `homeSystem`, no leaders/abilities;
- `lazax` (`other.json`, source `lazax`) — same as above.

**Playability criterion** (`FactionDef.is_playable`): a faction is playable when it has a
NON-EMPTY `homeSystem` AND a full set of leaders (`leaders`). This distinguishes placeholders
(both conditions false) from all real factions. Source: data structure (`other.json` file vs
the rest), not a rule from memory. Endpoint `GET /factions` returns only playable ones; setup
(`/setup/player`, `/game/new`) rejects unplayable ones (422).

**Firmament vs Obsidian (RESOLVED by data):** `firmament` (homeSystem `96a`) and `obsidian`
(homeSystem `96b`) are two HALVES of a single, double-sided Thunder's Edge home tile. During
setup, ONLY **Firmament** is selected; **Obsidian is NOT selectable** — it enters the game
exclusively via Firmament's action: "ACTION: Purge the Firmament's faction sheet, leaders,
planet card, and promissory note, then gain all of the faction components for The Obsidian."
Obsidian is brought into play by its ability THE BLADE'S ORCHESTRA (flip double-sided
components + ready Cronos Hollow / Tallin Hollow).

Rule in data (not from memory): Obsidian has the ability **`nocturne`**
(`assets/data/abilities/te_abilities.json`, `faction: "obsidian"`), whose `permanentEffect` =
"This faction cannot be chosen during setup." (additionally, franken errata marks `nocturne` as
`undraftable`). Therefore `FactionDef.is_playable` excludes factions having the `nocturne`
ability (constant `NO_SETUP_CHOICE_ABILITY` in `models.py`). Effect: `/factions` shows
Firmament, hides Obsidian; setup rejects Obsidian (422). If another "non-setup" faction is added
(e.g., the flip side of another tile), we tag it with the same ability in data — code needs no change.

**28.1 Keleres: one faction, three variants — MAX 1 per game.** Council Keleres appears in
AsyncTI4 data as three separate, playable entries (`keleresm`, `keleresx`, `keleresa`) — these
are variants of a single "mentor" of the same faction, sharing a common `shortName` "Keleres"
(see the note on faction family in `core/registry.py` → `faction_family`). A Keleres player
chooses ONE variant, so at most one representative of the family may appear in a single game.
Source: data structure (three entries sharing `shortName`) + faction clarifications in
[Council Keleres](../../../../rules_tirules/F_keleres.md); it is one faction, not three independent ones.

Enforcement in setup (`src/core/setup_service.py` → `_resolve_factions`):
- explicit choice of two different Keleres variants by different players → `ValueError` (HTTP 422),
  alongside the existing duplicate validation for the same `faction_id`;
- random selection ("random") picks at most one representative per family (`_playable_faction_pool`
  deduplicates by `faction_family`) and skips families already taken by an explicit choice —
  ensuring random assignment will not give two players two Keleres variants.
  Tests: `tests/test_setup_factions.py`.
