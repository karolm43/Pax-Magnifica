## 2a. Map String and Board Positions (AsyncTI4) — ✅ VERIFIED

📎 tirules: [Game Board](../../../../rules_tirules/R_game_board.md) · [System Tiles](../../../../rules_tirules/R_system_tiles.md) · [Mecatol Rex](../../../../rules_tirules/R_mecatol_rex.md)

Source: local AsyncTI4 asset `assets/alias/position_alias.properties`
(authoritative TTPG → Async positions mapping). Verified 2026-10 by comparison
against real data, not from memory.

**Map string format (TTS/AsyncTI4):**
- Space-separated sequence of tile IDs, e.g.
  `72 66 77 26 27 34 50 69 76 31 35 37 78 62 75 67 38 65 0 28 79 0 48 64 0 44 29 0 25 47 0 39 49 0 41 40`.
- **Mecatol Rex (system `18`) is DEFAULT at the center (`000`)** and does NOT appear
  in the string (unless the string starts with the center ID — explicit center variant).
- Tiles are assigned **sequentially** to positions in a fixed order (see below),
  ring by ring, starting from ring 1.
- **`0` = empty slot** (no tile at this position) — skipped when building the map,
  but OCCUPIES a position in the sequence (does not shift subsequent tiles).
- Length: 36 IDs = rings 1-3 (6 + 12 + 18). 3 rings is the standard map
  (up to 6 players). Longer strings include ring 4+.

**Position order (from `position_alias.properties`):**
- Center: `000`.
- Ring 1: `101 102 103 104 105 106` (6 positions).
- Ring 2: `201 .. 212` (12 positions).
- Ring 3: `301 .. 318` (18 positions).
- Ring N: `N01 .. N{6N}` (6N positions).
- Numbering goes **clockwise**, starting from the position
  directly ABOVE the center (`101` = above Mecatol).

**Coordinates (axial → cubic):**
- The file provides TTPG axial `(a, b)` ("doubled" layout): e.g. `101 = (0, +2)`.
- Conversion to cubic: **`q = a`, `r = (b - a) / 2`, `s = -q - r`**.
  Verified: `(b - a)` is always even; distance from center = ring number.
- NOTE: this orientation (AsyncTI4) differs from the earlier geometric
  generator `position_to_hex` from Block 2. The source of truth for positions is NOW the alias file
  (not standalone geometry), because it must mirror AsyncTI4's layout and numbering.
- Hex orientation during rendering: **flat-top** (matching AsyncTI4 tile graphics).

**Source:** `assets/alias/position_alias.properties`; map string format — TTS/AsyncTI4
standard (standardization group on the TTS Discord, cf. ti4-map-lab).

**Home positions (home systems) and empty `0` in the string — ✅ VERIFIED geometrically:**
- With 6 players, home systems sit at the **6 corners of ring 3**: positions
  `301, 304, 307, 310, 313, 316` (each has one cubic coordinate = 0, two = ±3).
- In a map string, these positions are usually `0` (empty), because the home tile depends on the chosen
  faction and is not part of the randomized map. Confirmed on the user's string:
  exactly those 6 positions were `0`.
- Code takeaway: `0` at a ring corner (when the ring has a full set of 6 home corners)
  is treated as a **player home slot**, not an ordinary void — we render a colored hex.

**Tile IDs and pre-built maps with home systems (2026-11-23):**
- We translate the token to an ID from AsyncTI4 data (`core/map_string.resolve_tile_id`): exact
  id → without/with leading zero (`8` = `08`) → alias from system data (`nekro`) → side `a`
  of a double-sided tile (`96` = `96a`, Firmament — starting side; Obsidian is not
  selectable in setup, RULES 28). Source: `aliases` field in `assets/data/systems`.
- A token unknown in active sources = 422 error with the list of tokens (previously a silent gap).
- A generator string (e.g. Milty) can contain **home tiles** at player seats. Seat =
  empty home corner or position with a playable faction's home tile (home from faction data
  or true off-board home: `51` Creuss, `118` Crimson) — `core/map_string.map_seats`.
- ⚠️ ASSUMPTION ("Auto"): a player sitting in such a seat gets that home's faction by default
  (wizard: `applySeatFactions`; backend `/game/new`: player without `faction_id`).
  The player may choose another — then its home replaces the tile. Switching seats in the wizard
  moves the faction along with the seat. An unoccupied home reverts to an empty slot
  (otherwise an absent faction's home planets would lie on the map).

**Player color order at corners — ⚠️ ASSUMPTION (to be confirmed):**
- This is NOT a TI4 rule (LRR does not enforce colors per position) — it is a display convention.
- Adopted layout (flat-top, top = `301`, clockwise):
  `301`=red, `304`=green, `307`=white, `310`=blue, `313`=purple, `316`=yellow.
- Mirrors the user's sample render. User makes final confirmation.

## 2b. Unit Classification: Space vs Planet — ✅ VERIFIED

📎 tirules: [Units](../../../../rules_tirules/R_units.md) · [Ships](../../../../rules_tirules/R_ships.md) · [Ground Forces](../../../../rules_tirules/R_ground_forces.md) · [Structures](../../../../rules_tirules/R_structures.md) · [Mechs](../../../../rules_tirules/R_mechs.md)

Source: TI Wiki/LRR — /wiki/Units, /wiki/Mechs, /wiki/War_Sun, /wiki/Infantry.
Content paraphrased for license compliance.

Units exist in **two disjoint locations** within a system:
- **Space** — ships standing in the space area of the system (participate in space combat).
- **Planet (ground)** — ground forces and structures ON a specific planet (ground combat / installations).

**Classification (placement):**

| baseType     | asyncId | Placement | Category     |
|--------------|---------|-----------|--------------|
| fighter      | ff      | space     | ship         |
| destroyer    | dd      | space     | ship         |
| cruiser      | ca      | space     | ship         |
| carrier      | cv      | space     | ship         |
| dreadnought  | dn      | space     | ship         |
| flagship     | fs      | space     | ship         |
| **warsun**   | ws      | **space** | ship         |
| **infantry** | gf      | **planet**| ground force |
| **mech**     | mf      | **planet**| ground force |
| **pds**      | pd      | **planet**| structure    |
| **spacedock**| sd      | **planet**| structure    |

**⚠️ WARNING — flags in AsyncTI4 data are UNRELIABLE for this classification:**
- In the data, `mech` has `isShip=True` and `warsun` has `isShip=False` — both wrong according to the rules.
  LRR: War Sun is a ship (space combat); Mech is a ground force (ground combat, holds planets).
- Therefore, we take placement from the **explicit rules table** (above), NOT from `isShip`/
  `isStructure` fields. The code maintains a static `asyncId → placement` map based on this table.

Representation in `GameState`:
- `SystemState.space_units[player_id][base_type] = count` — ships in space.
- `SystemState.planet_units[planet_id][player_id][base_type] = count` — ground forces/structures.

## 2c. `startingFleet` Format and Faction Setup — ✅ VERIFIED

📎 tirules: [Ships](../../../../rules_tirules/R_ships.md) · [Ground Forces](../../../../rules_tirules/R_ground_forces.md) · [Reinforcements](../../../../rules_tirules/R_reinforcements.md) · [Units](../../../../rules_tirules/R_units.md)

Source: AsyncTI4 faction data (`assets/data/factions/*.json`), verified on
base+pok (2026-10). Format paraphrased; pattern empirically confirmed.

**Faction fields relevant to setup:**
- `homeSystem` — home tile ID (e.g. Arborec → `05`, Muaat → `04`).
- `homePlanets` — list of home system planets (e.g. Hacan → `arretze, hercant, kamdorn`).
- `startingFleet` — starting fleet (format below).
- `startingTech`, `factionTech`, `commodities`, `preferredColours`.

**`startingFleet` format:** comma-separated tokens, each:
`[count] <code> [planet_suffix]`
- Count defaults to 1 (when omitted).
- Inconsistent separators (commas, variable spaces) — parser splits on comma and whitespace.
- **`startingFleet` unit codes** (DIFFERENT set from `asyncId`!):
  `cr`→cruiser, `cv`→carrier, `dd`→destroyer, `dn`→dreadnought, `ff`→fighter,
  `fs`→flagship, `ws`→warsun, `inf`→infantry, `mech`→mech, `pds`→pds, `sd`→spacedock.
  - ⚠️ Data inconsistency: Keleres (3 variants) uses `ca` for cruiser instead of `cr`.
    We accept `ca` as an alias for cruiser in the code map.
- **Planet suffix** = shortest **unambiguous prefix** of the home planet's name:
  - Present ONLY on ground forces/structures (inf, mech, pds, sd).
  - Ships (cr, cv, dd, dn, ff, fs, ws) have NO suffix → placed in space.
  - On a 1-letter collision, a longer prefix is used: Xxcha `archonren`/`archontau`
    → `ar`/`at` (since `a` alone is ambiguous).
  - Examples: Arborec `inf n` → nestphar; Hacan `sd a` → arretze, `inf k` → kamdorn.

**Player setup (result):**
1. The faction's home tile (`homeSystem`) goes into the home slot of the selected color.
2. `startingFleet` is deployed: ships → `space_units`; ground forces/structures → `planet_units`
   on the planet indicated by the suffix.
3. The player controls their home planets (`homePlanets` → `planet_owners`).
4. `startingTech` is set on the player state. **`commodities` is NOT the starting amount:**
   the faction field `commodities` is the **commodity value = MAXIMUM** (the cap to which
   the player "replenishes"). We store it as `commodity_value`, and **current
   `commodities` start at 0** — 📎 tirules [Commodities](../../../../rules_tirules/R_commodities.md):
   "A player starts the game with zero commodities". The viewer displays
   `commodities / commoditiesTotal` = current / `commodity_value`.

**Unit graphics:** `assets/units/<color>_<asyncId>.png`. NOTE: `asyncId` ≠ `startingFleet`
code (e.g. cruiser: `asyncId=ca`, fleet code=`cr`). Mapped via `baseType`.

## 2d. Player Neighbors — ✅ VERIFIED (partially)

📎 tirules: [Neighbors](../../../../rules_tirules/R_neighbors.md) · [Adjacency](../../../../rules_tirules/R_adjacency.md) · [Transactions](../../../../rules_tirules/R_transactions.md)

Source: tirules2.com → `docs/rules_tirules/R_neighbors.md`. Content paraphrased.

A PLAYER-level concept (who borders whom), distinct from static map adjacency
(section 2): system adjacency is the input, player adjacency is the output.

- Two players are **neighbors** if BOTH have a unit or
  control a planet in the **same system**.
- They are also neighbors when both have a unit or control a planet in systems
  **adjacent** to each other (adjacency via wormhole included — since it is part of
  adjacency from section 2).
- "Presence" in a system = unit in space, unit on a planet, OR
  planet control (`planet_owners`). Empty stacks (0 count) do not count.
- The relation is **symmetric**; a player is not their own neighbor.
- Significance: only neighbors can make transactions (R_transactions). The
  `neighbors` field in web-data feeds the player panel (neighbor icons) as a list of COLORS.

**Scope in code:** `src/core/neighbors.py` (`neighbors_of`, `neighbors_by_player`)
— pure functions over `GameState` + `HexGrid`. Serialization in `api/web_data.py`
maps `player_id` → color.

**⚠️ Limitations (to be expanded with the full adjacency layer):**
- System adjacency comes from `HexGrid` (geometry + wormholes); **hyperlanes**
  are not yet accounted for (as in section 2).
- Faction/agenda effects altering adjacency (e.g. Creuss *Quantum Entanglement*,
  Mentak through wormholes) are not modeled — they will enter via hooks when implemented.

## 2e. Promissory Notes: Hand vs Play Area — ✅ VERIFIED (model)

📎 tirules: [Promissory Notes](../../../../rules_tirules/R_promissory_notes.md) · [Transactions](../../../../rules_tirules/R_transactions.md)

Source: tirules2.com → `docs/rules_tirules/R_promissory_notes.md`. Paraphrased.

Promissory notes exist in THREE disjoint representations — a distinction
important for visibility (R2/R6) and for trading:

- **HAND** — notes held for potential trading. **SECRET**
  (private): others only see the COUNT (public — "the number of promissory notes
  in a player's hand is public information"), never the IDs. Model:
  `PlayerState.private.promissory_notes`; the count in web-data is `pnCount`.
- **PLAY AREA** — notes PLAYED and lying faceup (e.g. *Support for
  the Throne*, *Alliance*, which must be played immediately). **PUBLIC**: visible
  to everyone. "Promissory notes in the play area cannot be traded." Model:
  `PlayerState.promissory_notes_in_play`; in web-data the `promissoryNotesInPlayArea` field,
  which the player panel renders in the holdings rack (next to relics and secret objectives).
- **FACTION-OWNED (loadout)** — the unique note that EVERY player starts the game with
  (e.g. Sol `ms` = Military Support, Hacan `convoys` = Trade Convoys; Empyrean has two:
  `dark_pact`, `blood_pact`). This is a static, PUBLIC fact (faction X has note Y) read from
  faction data (`FactionDef.promissoryNotes`), NOT game state. In web-data the
  `customPromissoryNotes` field (helper `_faction_promissory_notes`); the panel renders them in
  the loadout section (next to faction abilities and techs), gated by `showPlayerAreaFactionAbilities`.

**⚠️ Scope:** the play area field exists and is PUBLIC (classified in `player_fields.py`),
emitted to the viewer and editable via God-Mode (`/player/{id}/edit`). Automatic
moving of a note from hand to play area when played will arrive with
transaction/promissory-note-play logic (timing windows, E8+). Until then, the operator populates the play area.
