### 44.1. The `actor_id` Rule (MANDATORY NOW for every new action endpoint)

- Every player action (non-God-Mode) in `api/` accepts an explicit `actor_id` — who performs it — and passes it to `core/`.
  Today it may be trusted (local mode, single window), but the field MUST exist so later authorization does not require
  changing signatures across dozens of endpoints.
- `core/` validates `actor_id` against the game state (it is the active player, current window respondent, or a player
  authorized for that action), just as it already does for `player_id` (e.g., `component_action`, RULES.md 31). One must not
  assume "the client is honest".
- `core/` remains network-unaware: it knows nothing about sessions, tokens, WebSockets, or HTTP. It knows only `player_id`.
- God-Mode actions (`/god-mode/*`, `core/board_edit.*`) have a separate permission (operator/host), not a player's `actor_id`.

### 44.1a. `actor_id` Mechanism in Code (design decision 2026-11-11)

- **Carrier: HTTP header `X-Actor-Id`**, NOT a request body field. The sole read point is the FastAPI dependency
  `api/actor.py::get_actor` — in stage N1 it is swapped for reading the seat token (44.2) and the rest of the code stays unchanged.
  Legacy `actor_id` fields in request bodies (action cards, offers, technologies, Thunder's Edge, hold) stay for compatibility:
  `core/actor.py::merge_claimed` merges them with the header, and header ≠ body mismatch is an authorization error.
- **No header = trusted mode (local, single window)**: `actor_id=None` passes every identity check
  (legacy behavior). In network mode `get_actor` NEVER returns `None` (no token → 401).
- **Classification of EVERY state-mutating endpoint** (POST/PUT/PATCH/DELETE) — strictly one of three:
  1. *player action* — `actor: ActorId` parameter; router calls `core/actor.py` (`subject`, `require`) with the list of
     authorized players derived from state (active player, window respondent, combat/invasion sides, decision owner, etc.);
  2. *table action* — also `actor: ActorId`, requiring only that the actor be seated at the table (`require_seated`):
     chess clock, opening epilogue;
  3. *operator/host* — `HostOnly` dependency (`api/actor.py::require_host`): God-Mode, editing board/players/decks,
     Undo/Redo/history, new game/map, manual windows and steps. Today it passes (locally operator = host); in N1
     it will check the `host` role from the token.
     Exception: `POST /tactical/undo-move` ("Undo last move" in the move step) — the ACTIVE player reverts strictly
     the last snapshot if it is a ship movement (`tactical:move:*`) or — if nothing has moved yet — the system
     activation itself (`tactical:activate:*`, with no open window/`held_play`; token returns to pool; the button reads
     "Undo activation" then, user decision 2026-11-23); otherwise 422 (user decision 2026-11-14).
  Guard test (`tests/test_actor_guard.py`) traverses all application routes and requires strictly one
  class — a new unclassified endpoint will fail QA.
- **Body "subject" field** (`player_id`/`faction` — whose decision/units it is) remains; `core/actor.subject`
  resolves it (faction → `player_id`), requires consistency with actor, and inserts actor if omitted.
  This lets actor flow into `core/` through the same path where `core/` already validates turns (RULES.md 31.2).
- **Authorization error**: `core/actor.ActorError` (subclass of `PermissionError`, NOT `ValueError`) → HTTP **403**
  (handler in `api/app.py`); rule errors unchanged → 422.
- Known gaps until N5: consent of the second party in a transaction (today initiator settles the whole thing), manual cycling of players
  in Agenda (`/turn/next-player` = host), manual opening of windows (`/window/open` = host).

### 44.2. Identity and Authorization (`api/` layer)

- Every seat at the table has a token (e.g., invite link). The token maps to `player_id`; `api/` determines `actor_id`
  from the token, NOT from the request body or a URL parameter.
- **View (`viewing_player`) cannot be a freely client-selectable parameter** in network mode —
  today it is a query parameter (RULES.md 6/web-data), which over the network would let someone peek at another player's hand. In network mode,
  the perspective comes from the token; in hot-seat/solo it stays as before.
- Role `host` (creates game, God-Mode, crash recovery) and role `observer` (no hands, public info only) —
  ⚠ ASSUMPTION to confirm.
- Authorization errors mapped in `api/` (not `core/`) to 401/403; rule errors still 422.

### 44.2a. Mechanism in Code (N1, 2026-11-11)

- Start: `uv run python -m src.api --network` (`create_app(network=True)`); prints host link `/?token=…`.
  Host token can be pinned via `CUSTODIAN_HOST_TOKEN` env var. Without the flag — local mode unchanged.
- `api/seats.py`: `SeatRegistry` (host token + token per seat, in process memory, NEVER in `GameState`),
  `Identity(network, player_id, host)`. Middleware in `app.py` reads `X-Seat-Token` (or `?token=`) and sets
  identity on `request.state.identity` + `current_identity`. Missing/bad token → **401**; without a token, only
  static data (assets, rules, factions, components) and `/network/me` may be fetched.
- On network, actor = player from token (`X-Actor-Id` ignored); `HostOnly` requires host role (otherwise 403).
- Host: unseated = operator (full state, trusted mode); `POST /network/host-seat` seats them at the table —
  then they see only their own, God-Mode stays. `GET /network/seats` (tokens, created on read),
  `POST /network/seats/{id}/rotate` (old link stops working).
- Frontend: link `…/game?token=…` → sessionStorage (token disappears from address bar) → header on `/bot…`;
  `NetworkPanel` ("You" badge, host invites, curtain when no token).
- ⚠ ASSUMPTION (to confirm): no `observer` role (no way to grant it); tokens are lost on restart (N3).

### 44.3. Per-Player Visibility (uses existing `core/visibility.py`)

- Every WebSocket connection receives its OWN state projection (`project_for_viewer`), never a shared broadcast of full state.
  The current `broadcast_map` (single message to everyone) may only be used for fully public data.
- Rule: the server sends a client only what that client is allowed to see. UI-side hiding is NOT security.
- Events (e.g., "card played", roll result) have a public/private type; private ones go only to authorized recipients.
- **In code (N2, 2026-11-11):** `core/visibility.project_strict(state, viewer)` = other players' hands → counts +
  facedown decks as `hidden` stubs (length public, composition/order not) + `rng_seed=0` (dice
  unpredictable) + other players' `pending_offers` without label/context + `pending_strategy.draft` only for
  owner. `StateService.envelope()` projects by request identity, so EVERY action response is
  safe; WebSocket `ConnectionManager.broadcast_each` builds a projection once per view key. `web-data` on network:
  perspective from token (parameter ignored), strict projection. GET with private data (`player_id`):
  `require_view` (others' → 403), `/offers` and hand narrowed to own. Map (`broadcast_map`) is public.
- Frontend: `useBackendPush` — WebSocket `/bot/ws?token=` as a refresh signal for active queries (shows other
  players' moves); disabled in local mode. Tests: `tests/test_network_game.py` (nothing leaks).
- Mandatory test for every new message: reveals no other player's cards, secret objectives, or numbers other than public ones
  (cf. 43.4: external behavior must not betray hand contents).

### 44.4. Rooms, Persistence, and Concurrency

- Multiple concurrent games: game identifier (`game_id`) in service state; today state lives in one process's memory and
  backend restart wipes the match. Target: persistence (`EventStore` on disk) and resume after restart.
- Actions within a single game are serialized (one lock per game); two actions at once cannot interleave.
- Idempotency: a repeated request (double click, retry after drop) must not execute an action twice
  (snapshot `seq` number in request or idempotency key) — ⚠ ASSUMPTION regarding mechanism.
- On reconnect, the client fetches full current state (its own projection) instead of replaying missed events.

**In code (N3, 2026-11-11) — match saving:** `python -m src.api` writes continuously to `saves/game.db` (SQLite:
state snapshots + Undo history + `meta` table); `--save FILE` selects another file, `--fresh` moves aside the old save (`*.old-*`),
an unreadable save is moved aside (`*.broken-*`), nothing is deleted. `meta` stores what is not in `GameState`:
tile placements (`HexGrid.to_placements`, saved in `AppContext.set_map/save_map`) and seat tokens
(`SeatRegistry.to_json`) — after restart, invite links keep working. After restart, the chess clock stays at the time of
the last action (downtime does not consume time). One match per process/file; "multiple concurrent games" (`game_id`) and
locking/idempotency — still PLAN. `saves/` is in `.gitignore` (contains tokens).

### 44.5. Concurrent Interactions and Absent Players

- Timing windows (RULES.md 29.2) already prompt players sequentially; on the network, UI shows "Waiting for player X".
  Where rules allow multiple players to act simultaneously (e.g., choices independent of each other),
  consider parallel responses — ⚠ ASSUMPTION, to decide after checking each case in tirules2.
- **In code (N5 part 1, 2026-11-11):** `core/actor.awaiting(state)` → `web-data.awaiting` (whose turn it is and what they must
  do; public). Frontend on network: "Your move / Waiting for X" bar, desk (`useDeskPlayer`) = always own seat,
  so turn controls automatically dim outside your turn; 403 denial shown as message; God-Mode (skip phase) host-only.
- Disconnect / no response: window timeout → bot takeover (difficulty from RULES.md 36)
  or pass — ⚠ ASSUMPTION pending user confirmation.
- STOP (43.4) requires a uniform protective pause independent of hand contents; single model for network and bots
  (hot-seat is not supported — user decision 2026-11-08).

### 44.5a. UI Lobby and Game Saves (user decision 2026-11-11: "lobby instead of cmd", ZeroTier network)

- **Host = computer running the server.** A request from loopback (including via Vite proxy: LAST entry of `X-Forwarded-For`,
  appended by proxy with `xfwd: true`) always has the host role — no token needed. Vite listens on all interfaces
  (`server.host: true`), so **when the lobby is closed, the backend serves only this computer** (others: 403;
  public static data — assets, rules, factions — available).
- **Lobby = live graphical wizard (user decision 2026-11-11):** "Play" (`POST /lobby/open {reset:true}`)
  opens a fresh lobby: the "Players & map" step is the lobby — host sets map, player count, bots; "Invite friends" panel
  with link (LAN/ZeroTier). A guest opens the link, enters their name (`POST /lobby/join`, `PublicJoin` marker) and takes
  the first open human seat (player card: "<name> · joined"; open: "Open seat – waiting…"). From there EVERYONE
  sees the same wizard: host drives steps, each guest picks THEIR faction, then color and seat — others' choices
  are visible live. Wizard draft lives on the server (`api/lobby_draft.py`: `slots`, `owners`, `mapString`,
  `step`, `version`): host `PUT /lobby/draft` (full) and `PATCH`; guest `PATCH` only fields of their own slot
  (`GUEST_FIELDS`; `LobbyParty` marker, other slots/steps → 403); faction/color/seat unique (→ 422). Frontend:
  `domains/network/setupSync.ts` (diffs → patches every 250 ms, poll every 1 s, `useLobbyRole`/`canEditSlot` in steps).
  Start game (host): `/game/new` + `POST /lobby/seat` — owner of slot `i` sits as `p{i+1}`, guest enters game automatically.
- **Host test mode:** the "who am I playing" badge has a toggle "Test: play for everyone" (`/network/host-seat null` —
  host-operator: desk = turn player, any action, full view) ⇄ "Back to my seat" (`host_home`).
- An unseated member sees the observer projection and cannot perform actions (403).
- **Saves:** one match = one file in `saves/`; a new game from the wizard starts a NEW file (`game-<date>.db`), the
  "Load game" menu (`GET /saves`, `POST /saves/load`) loads state, history, map, and seats (old links/tokens work).
  Starting the server without flags resumes the most recently modified match.
- "Who am I playing" badge in the game header (`WhoAmIBadge`): on network my seat, locally the turn player.

### 44.7. Player Undo (user decision 2026-11-16: "undo for players up to logical time, not only host")

Source: user decision (not a TI4 rule). Host retains full history Undo/Redo (God-Mode, `HostOnly`). Code: `core/player_undo.py`, router `api/routers/player_undo.py` (`GET/POST /undo/mine`), step author `EventStore.commit(author=)` (`author` column, from `seats.current_author` set in identity middleware: network = player from token, locally `X-Actor-Id`); frontend `BottomHandDock/UndoControls.tsx` ("Undo" button next to "Hold"); tests `tests/test_player_undo.py`, `UndoControls.test.tsx`.

- **What it undoes.** Strictly ONE'S OWN last step, one at a time; repeated Undo reaches further back (undo snapshots `player-undo:*` are transparent), as long as each consecutive step meets the conditions below.
- **"Logical time"** — a step can be undone when: (1) it was performed by a request from this player (bot / unseated host / technical operation — no; labels `initial`, `setup`, `god-mode`, `replace`, `hold-rewind`, `reaction-pause`, `clock:` never); (2) since then nobody else has acted; (3) the step is reversible as in hold-rewind (53.7: no dice, deck draw/shuffle, drawing a card to hand, phase/round change, playing an action card, `held_play`); (4) the active player has not changed (end turn, pass, picking a strategy card close Undo); (5) the step did not modify another player's state (transaction, their planets/units in `PlayerState`…); (6) the step did not open a protective pause and none is active (54.10).
- **Effect.** New snapshot = copy of state before the step (`replace_state(branch_from=…)`, undone steps drop from history), chess clock from the present (does not refund time). Without re-enforcing limits (`player-undo` in `_LIMITS_EXEMPT_LABELS`). Activity feed: `turn.undo` ("X undid their last step").
- ⚠ The legacy "Undo last move" (`/tactical/undo-move`) still moves the history pointer back without these prohibitions (e.g., after a Gravity Rift roll) — to be unified.
