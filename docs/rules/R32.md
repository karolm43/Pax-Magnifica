## 32. Ship movement: legality enforcement (tactical action) — ✅ VERIFIED (LRR 2.0)

Milestone E8-T5. Source: local LRR 2.0 — `docs/rules_tirules/R_movement.md`, `R_tactical_action.md`
(content © FFG; see SOURCE.md). Complements the draft in RULES.md 3 (which was "TODO") and
anomalies in RULES.md 1. Movement stops being God-Mode only — it becomes a VALIDATED action (RULES.md 29.1).

### 32.1. Movement rules (R_movement, "Move Ships" step) — ✅ VERIFIED

A ship moves to the ACTIVE system (tactical action, step 2), obeying:
- **(R1) Destination = active system.** A ship must END its movement in the active system
  (`GameState.active_system`). Movement outside a tactical action (without an active system) is
  illegal on this path (ability-based movement is a separate matter — not T5).
- **(R2) Range.** The number of systems a ship ENTERS (path length along adjacent systems) does
  not exceed its `moveValue`. NOTE: `moveValue` is taken from the PLAYER'S unit VARIANT
  (accounts for upgrades from owned technologies — `combat.resolve_unit_variant`), not the base
  entry. Example: base **Fighter** has `moveValue=None` (moves exclusively via transport using
  capacity), whereas **Fighter II** (technology `ff2`) has `moveValue=2` and can move on its own.
  Units with `moveValue=None` in their current variant do NOT move via this path (they move via
  transport — TODO capacity).
- **(R3) Cannot start with own CC.** A ship CANNOT move if it starts in a system containing the
  player's own command token (`SystemState.command_tokens` contains the player) — EXCEPTION:
  the active system (may "leave and return"). Source + R_movement note.
- **(R4) Not through enemy ships.** The path CANNOT pass through a system containing ANOTHER
  player's ships (even fighters alone block — R_movement note). INTERMEDIATE nodes must be free
  of other players' ships. The destination (active system) may have other players' ships (combat
  will occur there — step 3).
- **(R5) May pass through own CC.** The path MAY pass through systems containing the player's OWN token.
- **(R6) Anomalies / passability.** Supernova unconditionally impassable (cannot enter path —
  RULES.md 1.3). Asteroid field impassable without Antimass Deflectors technology (RULES.md 1.1).
  Nebula: entry only when it is the active system (RULES.md 1.2) — here we enforce the entry
  condition for intermediate nodes (intermediate nebula blocked). Path follows ADJACENCY edges
  of the graph (geometry + wormholes — RULES.md 2).
- **(R7) Starting in a nebula.** A ship that BEGINS the movement step in a nebula treats its
  move value as 1 for that step (R_nebula: "treats its move value as 1"); other effects (e.g.,
  Gravity Drive — `movement.move_value` hook) may increase it. Enforced in `movement.can_move`
  (audit 2026-11-11; previously omitted).

**⚠️ SCOPE OF T5 (intentional skeleton, "make it exist first"):**
- We validate and execute movement of a SINGLE stack of one ship type from a source system to
  the active system (`move_ships(state, grid, registry, from_pos, base_type, count, player_id)`).
  Multiple sources/types = multiple calls (or God-Mode). Declaring "all at once" and
  simultaneity belong to the UI/orchestration layer — for expansion.
- Transport of ground forces/fighters via `capacityValue` — ⬜ TODO (separate step; for now
  only ships move, capacity not counted). Marked in code.
- Antimass Deflectors: we check the player's owned technologies (`PlayerState.technologies`);
  technology alias from data (not from memory). When absent — asteroid field impassable.
- Pathfinding: shortest legal path (BFS over graph with intermediate node filter). If a path of
  length ≤ moveValue satisfying R4/R6 exists — move is legal. (Player does not choose the path
  manually in T5 — engine checks existence of a legal one; choosing path for gravity rift
  effects etc. = expansion.)

### 32.2. Model and implementation

- `core/movement.py` (NEW): `legal_move_destinations`/`can_move` (validation) + `move_ships`
  (execution: moves `count` ships of `base_type` from source to active system; mutates
  `space_units`). Pure functions `state -> state`.
- Strict validation: violating R1–R6 → `ValueError` → HTTP 422. God-Mode (`board_edit.move_units`)
  STILL bypasses (separate channel, no rules — RULES.md 25/26).
- Endpoint: `POST /tactical/move` (tactical router). UI will hook up in the movement step (MOVEMENT).

**Status:** ✅ T5 ship movement with R1–R6 validation (single stack). ⬜ path selection for
gravity rift, ⬜ ability movement — expansion. (Transport/capacity → 32.3 below.)

### 32.3. Transport (capacity) — ✅ VERIFIED (LRR 2.0 / tirules)

Milestone E8 Block B. Source: `docs/rules_tirules/R_transport.md`, `R_capacity.md` (content © FFG;
see SOURCE.md). Completes movement with carrying fighters and ground forces on ships.

- **(T1) Capacity = ship cargo limit.** A ship may transport any combination of fighters and
  ground forces, provided the total number of transported units does not exceed its
  `capacityValue` (from the player's VARIANT — upgrades count, e.g., Carrier/upgrade). Each
  fighter/infantry/mech occupies `capacityUsed` (usually 1).
- **(T2) Cargo moves together with the ship** and remains in SPACE of the destination system
  (does not land — landing is the INVASION step). Fighters are ships (`space`), but without
  their own `moveValue` they move exclusively as cargo (unless Fighter II — then they have
  their own movement). Ground forces (infantry/mech) during transport are in space as "cargo on a ship".
- **(T3) Where pickup is allowed (tactical action).** Cargo may be picked up from the ship's
  source system: from SPACE and from PLANETS of that system (source: R_transport "from the active
  system, the system it started its movement in, and each system it moves through"; "A ship may
  pick up ground forces from a planet"). Ground forces picked up from a planet ride in space as
  cargo and land only in Commit Ground Forces. ✅ Pickup from PASSED-THROUGH systems along the way:
  the player chooses a route (`route` = list of systems from source to active, validated like
  R4/R6, length ≤ moveValue of each ship), and picks up cargo from any system ON that route
  (`CargoPickup.from_position`; T4 checked per system). Ships travel one route together. UI
  preview: `GET /tactical/move-route` (route via waypoints `via`, alternatives, ships, cargo
  along the way; `core/movement_route.py`). ✅ Pickup from ACTIVE system (source: R_transport
  "from the active system"): last point of route, ground forces from planets only (cargo in
  destination space is already there), T4 does not apply to it.
- **(T6) Gravity rift on the route** (source: `rules_tirules/R_gravity_rift.md`, RULES.md 1.4).
  Each rift a ship EXITS (including start) or FLIES THROUGH gives +1 to movement; entering a rift
  (route destination) gives neither bonus nor roll. Nav Suite cancels bonus and roll. Before
  exiting a rift, each ship rolls a d10 (1–3 = removed from board, to reinforcements); rolls
  are recorded by `dice.record_table_roll(kind="gravity_rift")`. Cargo already loaded onto a
  removed ship disappears; cargo from later systems on the route for which surviving ships lack
  space stays behind. Without a specified route, the engine picks the shortest one, and when
  range requires the bonus — a route through rifts (`movement._auto_route`).
  ⚠️ ASSUMPTION: cargo is not assigned to specific ships (shared capacity) — excess over
  survivors' capacity is removed starting from the most recently loaded. To be confirmed by user.
  Out of scope: Vuil'raith Dimensional Tear as a rift, retreat from a rift (R39.5).
- **(T4) CC lock on pickup.** Cannot pick up fighters/ground forces from a system containing
  the player's OWN command token (exception: the active system).
- **(T5) Capacity limit in a system.** Total `capacityValue` of a player's ships in a system
  limits the number of fighters + ground forces the player may have in that system's space.
  Excess must be removed (player chooses). In Block B we enforce this as movement validation:
  cargo ≤ free capacity of the ships MOVING in this move.

**Model/implementation:** `core/movement.py` — new function `move_fleet(state, grid, registry,
from_pos, ships, cargo, player_id)` (ships/cargo = `{base_type: count}`): validates each ship
via `can_move` (R1–R6), computes free capacity (sum of `capacityValue` of ship variants − sum
of `capacityUsed` of cargo), and moves ships + cargo to the active system in `space_units`.
`move_ships` remains as a thin wrapper (single ship type, no cargo — backward compatibility).
Endpoint `POST /tactical/move` gets optional `cargo` field. Rule violation → `ValueError` → 422.
God-Mode (`/units/move`) still bypasses.

**Status:** ✅ transport from space AND from planets of source system (ships + cargo from
`from_zone`, capacity limit). ⬜ pickup from passed-through systems, ⬜ removing capacity excess
outside movement — expansion.
