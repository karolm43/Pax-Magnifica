## 3. Movement — ⬜ TODO (movement logic layer, later phase)

📎 tirules: [Movement](../../../../rules_tirules/R_movement.md) · [Move (Attribute)](../../../../rules_tirules/R_move.md) · [Transport](../../../../rules_tirules/R_transport.md) · [Active System](../../../../rules_tirules/R_active_system.md) · [Anomalies](../../../../rules_tirules/R_anomalies.md)

Verified rules to implement when the movement logic layer is built
(currently HexGrid only provides adjacency and distances):
- A ship must end its movement in the active system.
- Cannot move through a system containing another player's command tokens / ships.
- Cannot move if it started in a system containing its own command token.
- Number of systems on the path ≤ ship's move value.
- Anomaly modifiers from section 1 layer onto the above.
- Source: TI Wiki /wiki/Movement (reflects LRR Movement).

## Changelog of Code Changes Resulting from Verification

- **2026-10**: Anomaly verification revealed that HexGrid conflated adjacency
  with traversability. A Supernova should NOT remove adjacency edges (adjacency
  exists; only movement is blocked). An Asteroid field blocks movement conditionally
  (depending on player technology), so it cannot remove static edges either.
  → HexGrid redesigned: graph = pure adjacency (geometry + wormholes);
  traversability/blocks moved to per-system anomaly metadata for use
  by the future movement layer.

## 3a. Unit Plastic / Supply Caps — ✅ VERIFIED

📎 tirules: [Reinforcements](../../../../rules_tirules/R_reinforcements.md) · [Units](../../../../rules_tirules/R_units.md) · [Fighter Tokens](../../../../rules_tirules/R_fighter_tokens.md) · [Infantry Tokens](../../../../rules_tirules/R_infantry_tokens.md)

Source (NOT from memory): AsyncTI4 bot,
`TI4_map_generator_bot/src/main/resources/positions/reinforcements.properties`.
`Player.getUnitCap(unit)` returns the number of positions (coordinate pairs) for a given unit
in the reinforcements layout = number of plastic pieces a player has in their supply. Monument = 1 (special
case in `Player.getUnitCap`). Confirmed against live AsyncTI4 game data.

Caps per `asyncId` (encoded in `src/core/unit_catalog.py` → `UNIT_CAP_BY_ASYNC_ID`):

| asyncId | unit | cap |
|---|---|---|
| gf | infantry | 12 |
| ff | fighter | 10 |
| mf | mech | 4 |
| dd | destroyer | 8 |
| ca | cruiser | 8 |
| cv | carrier | 4 |
| dn | dreadnought | 5 |
| fs | flagship | 1 |
| ws | warsun | 2 |
| pd | pds | 6 |
| sd | spacedock | 3 |
| monument | monument | 1 |

Usage: `playerData.unitCounts[asyncId] = {unitCap, deployedCount}` in the
`web-data` document. The frontend reinforcements panel shows `unitCap - deployedCount` (how many remain
in the supply). `deployedCount` = count of that player's pieces of a given type on the board.
