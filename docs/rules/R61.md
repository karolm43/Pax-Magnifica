## 61. Faction Foundations — Leaders, Promissory Notes, Abilities, Breakthroughs
📎 tirules: [Leaders](../../../../rules_tirules/R_leaders.md) · [Leader Sheet](../../../../rules_tirules/R_leader_sheet.md) · [Purge](../../../../rules_tirules/R_purge.md) · [Promissory Notes](../../../../rules_tirules/R_promissory_notes.md) · [Promissory notes notes](../../../../rules_tirules/C_promissory_notes.md) · [Abilities](../../../../rules_tirules/R_abilities.md) · [Breakthroughs](../../../../rules_tirules/R_breakthroughs.md) · [Component Action](../../../../rules_tirules/R_component_action.md)
Texts of leaders, promissory notes, abilities, and breakthroughs come exclusively from assets (`assets/data/leaders`, `promissory_notes`, `abilities`, `breakthroughs`). The player decides themselves (R56). Plan: `docs/PLAN_FRAKCJE.md` (F1–F3).

### 61.1 Leaders — lifecycle (`core/leaders.py`)
- **State** (`PlayerState.leader_states`, missing entry = default): agent `unlocked` (ready), commander/hero `locked` (R_leaders). States: `locked`, `unlocked`, `exhausted`, `purged`. State changes in game logic only via `leaders.py` (God-Mode: `board_edit.set_leader_state`, also `purged`).
- **Unlock** = "Unlock" condition from data (`unlockCondition`). State predicate: `leaders.register_unlock("<leader id>")` or `register_unlock_condition("<condition text>")` (shared text, e.g., "Have 3 scored objectives." — all heroes). `leaders.refresh_unlocks` after EVERY commit (`StateService.replace_state`, outside God-Mode/setup). Event-based condition ("Resolve a combat…") = event hook in the faction module calling `leaders.unlock`, with `covers="unlocks:<id>"`. Unlocking fires `COMPONENT_GAINED/WHEN` (`component="leaders:<id>"`).
- ✅ R_leaders: "unlock conditions cannot be met while an ability … is being resolved" → no checking while offers (`pending_offers`) are open.
- ✅ R_leaders: an unlocked leader never returns to `locked`.
- ✅ Hero: 3 scored objectives, any combination of public (`objectives.scored`, only real objectives from catalog) and secret (`scored_secrets`); non-objective VPs (Custodians, SftT…) do not count.
- **Leader without coded condition** — the player unlocks it themselves (`leaders.claim_unlock`, `POST /leader/claim-unlock`) so the game does not stall (status MANUAL). A leader with a predicate unlocks only automatically.
- **Usage cost** from text: "exhaust this card" → `exhausted` (readies in status step 6), "purge this card" → `purged`. ✅ R_leaders: "A hero is purged after its abilities are resolved" — a hero with `ACTION:` is also purged when the data does not repeat "purge" (e.g., `ghosthero`). ⚠️ ASSUMPTION: a hero attached to a planet ("attach this card", Titans — R_leaders explicitly) is not purged. Xxcha hero: ✅ user decision 2026-11-16 — the game uses the Thunder's Edge version (`xxchahero-te`, `ACTION:` + purge), which replaces Codex (`xxchahero`) via `homebrewReplacesID` (leader loader, RULES.md 62.9).
- A purged or locked leader is not a hook source (`rules_hooks.owned_sources`).

### 61.2 Promissory notes — playing, play area, return (`core/promissory_play.py`)
- **Copy vs template.** In hand lies a color-prefixed copy (`red_cf`), in data the template (`<color>_cf`). `promissory_play.resolve` → (template, owner): color note = player of that color, faction note = player of that faction (including faction family). UI text includes the owner's color.
- ✅ Own note forbidden (R_promissory_notes: "cannot play their color's or faction's promissory notes").
- **Window.** A note with `ACTION:` = turn component action. Others are REACTIONS in the action card window model (RULES.md 53.5): playable when the engine NOW has an open window matching the note's text (`reaction_cards.open_windows`, addressed via `classify_window` of text before the first ":"). "The <color> player …" in the window = event subject is the note owner; "you …" = the player playing it. Additional condition: `promissory_play.condition("<template>")`. The engine never asks "do you have the note" (hand is hidden).
- ✅ **After effect** (return after full resolution): `playArea` → faceup in the player's play area (`promissory_notes.place_in_play`), "purge this card" → disappears, otherwise returns to the owner's hand (`return_from_hand`).
- ✅ **"When you receive this card … must place it faceup"** (`playImmediately`: Alliance, SftT) — `promissory_notes.transfer` calls `promissory_play.on_received`: the note enters play area immediately, the note effect receives `params["__received"]`. An owner receiving their own note keeps it in hand (no effect).
- Hooks for notes in play area: source `SOURCE_PROMISSORY` with both copy id AND template id (`<color>_sftt`).
- API: `GET /promissory/playable`, `GET /promissory/{id}/form`, `POST /promissory/play` (feed tag `promissory:<player>:<note>` — note is public once played).
- **Generic notes** (`core/hooks/promissory_generic.py`):
  - *Ceasefire* — owner's `SYSTEM_ACTIVATED/AFTER` window, condition: active system contains the playing player's units. Effect `Duration.TACTICAL_ACTION` on owner; `movement.can_move` refuses movement into the active system. ✅ ruling 3: ground forces on planets of the active system may still board ships ALREADY in its space (`movement.move_fleet` with no moving ships → `_load_in_active_system`, capacity-checked; ⚠️ ASSUMPTION: offered only under Ceasefire; UI for this gesture is not wired yet).
  - *Political Secret* — `AGENDA_REVEALED/WHEN` window. Owner: `agenda_phase.block_voter` + `Duration.AGENDA` effect blocking action cards (`action_cards.playability/play_action_card`) and ACTION faction abilities (`faction_components.block_reason`). ⚠️ Passive faction abilities in the agenda phase check `promissory_play.silenced` in their hooks (faction blocks).
  - *Support for the Throne* — upon receipt +1 VP (`objectives.award_points`); holder's `SYSTEM_ACTIVATED/AFTER` with owner's units in the system → −1 VP and return. ⚠️ "if the <color> player is eliminated" — elimination is not yet in the engine.
  - *Trade Agreement* — window "when the <color> player replenishes commodities": trace `GameState.last_replenished` (set by `economy.replenish_commodities`, cleared by `action_budget.clear_reaction_traces` on the next action). Effect: all of owner's commodities → to holder as TG (`economy.give_to_player`, R_commodities). ⚠️ ASSUMPTION: window lasts until the next action; owner's commodities at the time of play count.
  - *Alliance* — in holder's play area; `owned_sources` gives them the source of the owner's UNLOCKED commander (`promissory_generic.alliance_commanders`); a commander with a use window ("When you cast votes…") is also in the holder's components (`faction_components.borrowed_commanders`, F_hacan Gila 1.2). Return like SftT (without VP).

### 61.3 Faction abilities, breakthroughs, `ACTION:` leaders (`core/faction_components.py`)
- A faction component with an `ACTION:` header (leader: `abilityWindow`, ability: `window == "ACTION"`, breakthrough: text) is played via `component_action.play_component_action(component_id="<kind>:<id>")` — `leader:`, `ability:`, `breakthrough:`. Effect: `register_effect("leaders|abilities|breakthroughs:<id>")` + `register_effect_inputs`; condition: `faction_components.blocker(kind, id)`.
- Cost is paid by the common layer AFTER the effect (`faction_components.pay_cost`): leader per 61.1, breakthrough with "Exhaust this card" → `breakthrough_exhausted` (✅ R_breakthroughs: passive part and synergy keep working). Offer hooks ("you may exhaust this card") call the same function.
- Without a coded effect: action recorded, cost paid, `implemented=false` (effect applied manually, God-Mode).
- API: `GET /faction-component/playable`, `GET /faction-component/{kind}/{id}/form`, `POST /faction-component/play` (feed tag `component-use:<kind>:<id>`).

### 61.4 Faction units and faction package
- `UnitDef.ability` = ability text from unit data (flagships, mechs, faction upgrades). Hook source `SOURCE_UNIT` with the VARIANT id the player uses (`combat.resolve_unit_variant` with technologies and breakthrough; `rules_hooks._unit_sources`). Coverage key `units:<id>`. "In this system / this unit" abilities check presence via `core/faction_units.py` (`has_unit_in`, `positions_with`, `count_in_system`).
- Faction hooks: package `core/hooks/factions/<faction>.py` (Arborec moved from `factions_base.py`). Completeness test: `tests/factions/completeness.missing_components` — every faction component (ability, faction technology, leader + commander/hero unlock condition, breakthrough, note, unit with ability) implemented or explicitly MANUAL.

### 61.5 Unit capture (`core/capture.py`, block I1)
📎 tirules: [Capture](../../../../rules_tirules/R_capture.md) · [Blockaded](../../../../rules_tirules/R_blockaded.md) · [Vuil'raith](../../../../rules_tirules/F_vuilraith.md)
Shared mechanics for all "capture" components (Cabal, Mentak TE, Puppets of the Blade…). Captured-unit state changes ONLY via `core/capture.py` (central point, RULES 43.1a).
- **State** (`PlayerState`, public): `captured_units = {original owner: {base type: count}}` — non-fighter ships and mechs sit on the capturer's faction sheet (including the capturer's OWN units, e.g., Cabal flagship); `captured_tokens = {"fighter"|"infantry": count}` — R_capture: a captured fighter/infantry returns to the owner's reinforcements, and the capturer places a token from the supply onto their sheet (tokens belong to no one).
- **Owner's reinforcements** (`production.reinforcements_left`): a player's captured ships/mechs are out of their reinforcements — "cannot be produced or placed by its original owner until it is returned". Capturer's own units too — but R_capture Notes 5 (tirules2 2026-11-22): "A player who captures their own units may return them to their reinforcements at any time. They cannot place their own captured units unless instructed" → `capture.return_own`, `POST /capture/return-own` (actor = that player), UI: click own ship/mech in own `Nombox` → "Return 1 to reinforcements"; Activity `capture.return_own`. Fighter/infantry tokens belong to no one — not returnable this way.
- **Destruction → capture**: `unit_ops.remove_units(cause=DESTROYED)` asks `capture.on_destroyed`: PERMIT hook `capture.destroyed` (ctx: `player`, `base_type`, `position`, `zone`, `combat`) of each player in turn; the first that allows captures it (a unit is captured at most once). Structures never (R_capture "non-structure"; F_vuilraith: Hel Titan is a PDS).
- **From reinforcements** (`capture.from_reinforcements`, Vortex, The Stillness of Stars): ship/mech only when the owner has one in reinforcements (F_vuilraith Vortex 3); fighter/infantry always (token from supply).
- **From board without destruction** (`capture.from_board`, Dimensional Anchor): unit removed with `UnitCause.REMOVED` (F_vuilraith hero 1: "not destroyed").
- **Blockade** (R_blockaded, R_capture): (a) a player whose space dock is blockaded does not capture units of blockading players — neither ships nor tokens (Notes 4); during space combat in the dock's system both sides have ships, so there is no blockade (Notes R_blockaded 1). (b) When the original owner blockades the capturer's space dock, their ships/mechs return to their reinforcements IMMEDIATELY — `capture.release_blockaded` after EVERY step (`step_settle.settle_step`), so the end of the space combat step returns them before invasion (Notes 2). Fighter/infantry tokens do not return due to blockade.
- **Return** (`capture.return_unit`): ship/mech → original owner's reinforcements; token → supply. Only to the original owner (Notes 3). Owner eliminated → unit returns to the box (Notes 5) — disappears from sheet.
- **Transaction**: a captured ship/mech may be given in a transaction, but only to its original owner (`TransactionSide.captured_units`, base types); fighter/infantry tokens may not (R_capture).
- **Spending a captured unit** as cost (Amalgamation, Riftmeld): the player specifies whose unit they return (owner or token) — that is a regular return above.
- **View**: player web-data `nombox = {owner faction: ["<type>,<count>"]}` (`Nombox` component in player panel); tokens under the capturer's faction.
- ⚠️ ASSUMPTION: Nekro/Yssaril copying an ability capture, but do not spend (Notes 4) — to be handled in those factions' blocks.

### 61.6 Faction tokens on the map (`core/faction_tokens.py`, block I2 — Titans of Ul scope; Creuss wormhole tokens `creussalpha/beta/gamma` in the space zone since B15, RULES.md 62.19)
📎 tirules: [Ul](../../../../rules_tirules/F_ul.md) · [Muaat](../../../../rules_tirules/F_muaat.md) · [Abilities](../../../../rules_tirules/R_abilities.md)
Layer of faction tokens lying in a system zone (space or planet), independent of units. Mutated ONLY via `core/faction_tokens.py` (central point, RULES 43.1a). Currently one kind: **sleeper** (Titans of Ul); breach, galvanize, Creuss wormholes will be added in those factions' blocks.
- **State** (`SystemState.faction_tokens`, public): `{zone: {kind: owner}}` — zone = `space` or planet id; at most 1 token of a given kind per zone (F_ul Terragenesis: "a planet that does not have a sleeper token"). God-Mode sets the field via `systems` in `/god-mode/patch`.
- **Supply** (`faction_tokens.SUPPLY`): sleeper ×5 — count from AsyncTI4 (`WebPlayerArea`/`PlayerAreaGenerator`, same as in faction selection scene `factionComponents.ts`). Supply = 5 − player's tokens on the board; none in supply = token cannot be placed, can only move one already on the board (Terragenesis: "place or move").
- **Operations**: `place` (from supply), `move` (from another zone), `remove` (returns to owner's supply). Events: every change is an entry in the Activity feed (`faction_token` / `faction_token_removed`).
- **Board changes under a token**: tile swapped (Muaat Nova Seed — F_muaat: "any Ul sleeper tokens are returned to the Ul player") or planet destroyed → tokens return to owner's supply (`tile_swap`, `system_planets`).
- **View**: planet web-data — `sleeper` token (`entityType: "token"`, key `neutral`, graphic `token_sleeper.png` from frontend directory); supply in `playerData[].sleeperTokensReinf` (player token bar).

### 61.7 Player-dependent adjacency (`core/board_graph.py`, block I3)
📎 tirules: [Adjacency](../rules_tirules/R_adjacency.md) · [Wormholes](../rules_tirules/R_wormholes.md) · [Neighbors](../rules_tirules/R_neighbors.md) · [Creuss](../rules_tirules/F_creuss.md)
Four layers, from the bottom up — layers 1–3 ONLY add edges, layer 4 is the only one that removes them:
1. **Map topology** (`HexGrid`): shared edges + matching wormholes (tile and token) + Fracture portals. Same for everybody (R_adjacency rules-reference/1, R_wormholes rules-reference). Never mutated by effects.
2. **Tactical-action adjacency** (`action_adjacency`, hook `movement.extra_adjacent` of the ACTIVE player): Spatial Conduit Cylinder, Lazax Gate Folding — valid for all players during that action (RULES.md 62.3, 62.7).
3. **Player-dependent adjacency** (NEW, hook FORBID `adjacency.extra_for_player`, ctx `position`, `grid`): systems that are adjacent to `position` ONLY for the owner of the effect, persistently (e.g. Creuss *Quantum Entanglement*: "You treat all systems that contain either an alpha or beta wormhole as adjacent to each other" — the hook itself comes in block B15).
4. **Player-dependent cut** (block B16, hook FORBID `adjacency.cut_for_player`, ctx `position`, `grid`): systems that are NOT adjacent to `position` for that player although layers 1–3 make them adjacent — Empyrean *Void Tether*: "other players do not treat those systems as adjacent to each other unless you allow it" (even with matching wormholes — F_empyrean void-tether 1). Read in `neighbors_for_player` / `are_adjacent_for_player` / `movement_paths._neighbors_for_move` / `neighbors.neighbors_by_player` (a pair across a cut edge stays neighbours when only ONE of them is cut — void-tether 1.1). RULES.md 62.20.
- **Single central point**: `board_graph.extra_adjacent_for_player` / `neighbors_for_player` / `are_adjacent_for_player` (layers 1+2+3). Never `if faction == …`. A system is never adjacent to itself (R_adjacency rules-reference/2.1, R_wormholes notes/3) — the position itself is dropped from hook output. Hooks must return a symmetric relation (`b ∈ extra(a)` ⇔ `a ∈ extra(b)`); `are_adjacent_for_player` additionally checks both ends.
- **Whose adjacency** — the player who USES it (F_creuss Quantum Entanglement rulings):
  - **Movement / retreat** (`movement_paths._neighbors_for_move`, `retreat.*_destinations`): the moving player's layer 3. Traversability (anomalies, blockades, command tokens, Enforced Travel Ban on *map* wormhole edges) stays a separate layer, applied per system as before; layer-3 edges are not "map wormholes", so `wormhole_link_blocked` does not cut them (F_creuss: "The effect of the Enforced Travel Ban law does not affect the Creuss player").
  - **Space Cannon** (Deep Space Cannon from adjacent systems, `space_cannon.offense_shooters` and the "Space Cannon range" lens `coverage`): the SHOOTER's layer 3 — "Other players cannot use Quantum Entanglement to produce hits from a unit with the Deep Space Cannon ability against the Creuss player's units" (F_creuss).
  - **Neighbors / transactions** (`neighbors.neighbors_of`, `neighbors_by_player`; transactions, Pillage, objectives use them): players A (in system X) and B (in system Y) are neighbors if X, Y are adjacent in layers 1+2 OR in A's layer 3 OR in B's layer 3 — F_creuss: "the Creuss player and that player are neighbors" (relation stays symmetric).
  - **Effects that hit "units in/adjacent to a system"** (Ixthian Artifact, Stellar Converter, card targets) keep pure map adjacency (`board_graph.adjacent_positions`) — F_creuss: Ixthian "will not affect the Creuss player's units in a system with a beta wormhole". Effects phrased from a player's perspective that should honour layer 3 migrate to `neighbors_for_player` in their own faction blocks.
- **UI**: adjacency indicators come from the backend — movement reach (`/tactical` path endpoints, `movement_paths`), Space Cannon range lens (web-data `tileUnitData[].pds` ← `coverage`), neighbors (web-data `playerData[].neighbors`) — so they follow the same layers. Frontend `tileAdjacency.ts` is geometry for drawing control borders only (not a rules indicator).
- ⚠️ R_adjacency rules-reference/4 (hyperlanes): hyperlane tiles are not modelled as line connections — they sit in the grid as plain hexes (status `gap` in `tests/rulings_status.json`).
