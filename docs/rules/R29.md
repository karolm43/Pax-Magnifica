## 29. CHANGE OF DIRECTION: engine-as-REFEREE + timing windows (replaces "assistant, not referee")

📎 tirules: [Strategic Action](../../../../rules_tirules/R_strategic_action.md) · [Strategy Card](../../../../rules_tirules/R_strategy_card.md) · [Space Combat](../../../../rules_tirules/R_space_combat.md) · [Space Cannon](../../../../rules_tirules/R_space_cannon.md) · [Modifiers](../../../../rules_tirules/R_modifiers.md) · [Abilities](../../../../rules_tirules/R_abilities.md)

**Decision date: 2026-10. Agreed with user — INTENTIONAL change of project philosophy.**

### 29.1. New design decision (supersedes previous "table assistant, not referee")

The previous decision (sections 19-22, 24, 25, 27 and memory `engine-is-table-assistant-not-referee`)
stated: the engine GUIDES through steps and provides numeric aids, but does NOT validate rules —
players play physically and enter the outcome. **This decision is REPLACED.**

**New direction:** the engine ENFORCES TI4 rules in code (it is the REFEREE). Reasons (agreed with user):
1. The target AI bot must know and respect the rules anyway — enforcement in `core/` is its "world rules".
2. Enforcement is more convenient (user friendly) for the player — no need to remember and police legality.
3. The game stops assuming the player has a physical board laid out.

**God-Mode REMAINS** as a separate, intentional manual correction channel that BYPASSES validation
(safety valve for forgotten/edge cases). Rule: normal actions (movement, activation, pick,
production, combat) are validated STRICTLY (illegal → `ValueError` → HTTP 422); God-Mode
(`/god-mode/patch`, `board_edit.*`) intentionally does not validate rules — it is the "operator's hand".

**Game mode (decided; updated 2026-11-08):** networked game (humans) + bots; solo against bots
is a special case. Hot-seat is NOT supported (older mentions of it in docs are historical).
Therefore timing windows must prompt players IN TURN (queue), rather than assuming a single operator.

**Scope of first combat implementation (decided):** core first — dice rolls + hit counting +
"assign hits" window (defender chooses which units are destroyed), multi-round. Variants
(anti-fighter barrage, space cannon offense) added as SUBSEQUENT timing windows after the core.

> Sections 19-22 remain valid as a TI4 mechanics REFERENCE (step sequence, planet takeover,
> combat stats from UnitDef), but their annotations "does NOT validate / assistant, not referee"
> are SUPERSEDED by this section. As each is implemented, validation enters `core/` per 29.1.

### 29.2. Timing window model — ✅ VERIFIED (LRR "Timing" + AsyncTI4 + user confirmation 2026-10)

Source: LRR 2.0 entry "Timing of Component Abilities" / "Strategy Phase" (secondary order);
AsyncTI4 `service/strategycard/` (secondary/follow queue). Confirmed by user 2026-10.

**What a timing window is:** a moment in gameplay where ONE or MULTIPLE players have an
opportunity to make a reactive decision/action (e.g., strategy card secondary, reacting with
an action card, assigning combat hits). A window has a QUEUE of players prompted IN TURN and
closes once all have responded.

**Response order (CONFIRMED):**
- The queue starts with the player AFTER THE ACTIVE PLAYER (to their left / next in speaker
  order) and proceeds CLOCKWISE (speaker order rotated starting from the player after the initiator).
- **Strategy card secondaries:** after the active player resolves the primary, the remaining
  players resolve the secondary in this order; each may resolve the secondary OR decline (pass).
- **"When/after" reactions (action cards, technologies):** modeled UNIVERSALLY with the exact
  same mechanism — a queue of players prompted sequentially in the same order.
- **The window initiator** is SKIPPED in the queue by default (the window is for reactions by
  the others). Windows that exceptionally also apply to the initiator can include them
  explicitly (a parameter when opening the window).

**State model (implementation plan — Task 1):** a uniform field on `GameState` (e.g.,
`pending_window`): window type, queue of `player_id`s to prompt, current responder pointer,
who has already responded, context data (e.g., strategy card number, combat system position).
Pure functions in a new `core/timing.py` module: `open_window`, `current_responder`,
`respond_current`, `advance_window`, `close_window`. A single concept handles: strategy card
secondaries, space cannon, combat hit assignment, reactions.

**Applications (planned milestones):**
- Task 3: strategy card secondaries (first real window).
- Task 7/9: "assign hits" window, anti-fighter barrage, space cannon offense in combat.
- Future: action card / technology reactions (milestone E4).

### 29.3. "Current player / whose turn" concept — extension

`GameState.active_player_id` (single value) remains as "whose turn". Timing windows introduce
ALONGSIDE it "who reacts now" (the current window responder from 29.2) — a separate pointer
that does not overwrite the active player. STATUS/AGENDA stop clearing the active player
(Task 4) — they receive the proper order (initiative for status, speaker order for agenda;
to be confirmed in those milestones).
