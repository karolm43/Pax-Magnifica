## 65. Bot AI — Decision Layer Design Rules (2026-11-16)
📎 related: RULES.md 29 (Referee), 43.4 (STOP), 44.1a (actor), 44.5 (absent players), 56 (player decisions)

These are NOT TI4 rules: TI4 has no bot. This is the contract between the engine (`core/`) and the bot layer
(`src/engine/`). Design defaults confirmed by user decision (2026-11-27)
(`docs/bot/PLAN.md` §6). Work plan: `docs/bot/PLAN.md`.

### 65.1 Single rules path
- A bot performs moves exclusively as an `Action` from `src/engine/actions`, applied through the same `core/` functions
  called by `api/` routers. Actor = bot's `player_id` (RULES.md 44.1a, same 403/422 as a human).
- The bot does not use God-Mode (`core/board_edit.*`) or Undo. ⚠️ ASSUMPTION: after a human Undo, the bot decides anew
  from the current state.
- Outcome of a move = action + post-step settlement (`core/step_settle.settle_step`: game end, Nexus, limits,
  leaders, reaction pause, clock), i.e. the same thing server commit does (`StateService`). Bot simulations
  use `apply_and_settle`, not the action alone.
- Any missing rule or legal-move enumerator goes into `core/` (with a section in `docs/rules/`), never into `engine/`.
- Design debt (already in code, to be moved): `core/transaction.bot_accepts` and `core/epilogue._bot_choice`
  are bot decision placeholders in the rules layer; eventually `core/` asks, `engine/` answers.

### 65.2 Information
- The bot decides on `visibility.project_strict(state, bot_id)` — without others' hands, secret objectives, or `rng_seed`.
- Bot observation (`src/engine/observation.py`) = strict projection + OWN prompts computed by `core/`
  on the full state, exactly like the client's GET endpoints: strategy card step options
  (`strategic_action.step_options`, e.g., agendas peeked via Politics) and own offers with options
  (`offers.offers_view`). Nothing beyond what a human sees in that seat.
- Simulations sample hidden opponent information from the pool of cards invisible to the bot (determinization);
  they never read them from the full state.

### 65.3 Computation (user decision 2026-11-16: several separate complex algorithms computed locally)
- Algorithm = separate module behind a common interface (`DecisionRequest → DecisionResult`); mapping
  "decision → algorithm + parameters" in `assets/config/engine_config.json`, not in code.
- Heavy computation in worker processes on the host machine; the game server must not block.
- Every decision has a budget (deadline and/or iteration count). After the deadline: best result so far or
  default move (65.4). ⚠️ ASSUMPTION: budget values are set by the user.
- A result computed for a stale state (different `state_seq`, e.g. after Undo) is discarded.
- A fast state representation for simulation (if created) must yield the exact same results as `core/`
  (conformance test); it may not have its own rules.

### 65.4 The game never stalls
- ⚠️ ASSUMPTION: every decision type has a safe default move: pass in a timing window, decline a "may" offer
  (mandatory decision: first form options), skip secondary ("free" player from Trade: execute),
  play strategy card with minimal primary choices (no spending, skip research; Politics:
  first other player as speaker, peeked agendas back on top; Warfare: activate home system
  and immediately end tactical action; Construction: first legal structure), pass turn, abstain
  from voting, speaker on tie: first outcome; token redistribution unchanged (new tokens to tactics pool);
  hit assignment: Sustain Damage first, then units with worst combat value.
- Fixed-duration windows (reaction pause, hold-play) are closed by any player after timeout (`*_release`).
- An all-bot game must reach completion without intervention (arena test).

### 65.5 Determinism and time
- `engine/` does not use `time.time()`, `secrets`, or unseeded `random`; seed and deadline come from outside.
- Same projection + seed + iteration budget = same decision (inline mode). A millisecond deadline
  gives determinism only in iteration-limited mode — arena and tests use iteration limits.

### 65.6 Difficulty levels and personalities
- ⚠️ ASSUMPTION (as in `engine_config.json`): EASY/NORMAL/HARD and personalities are bundles of algorithms,
  parameters, and budgets; the bot receives no rule advantages at any level.

### 65.7 Server-side bot trigger (user decisions 2026-11-16, PLAN §6 items 2–6)
- The bot plays in the server process (`api/bot_runner.py`); heavy computation in a worker process pool
  (`workers: 0` = all cores except one). Separate network client: no.
- A bot move goes through the EXACT SAME HTTP request as a human move (internally via ASGI, `api/bot_http.py`):
  same history labels, Activity, middleware, and broadcast. In networked games the runner authenticates with
  a token known only to the server process (`SeatRegistry.bot_token`); actor = `X-Actor-Id` header.
- The runner wakes after every state broadcast and every second (fixed-duration windows expire over time).
- Budget: 2 s regular decision, 10 s key decision (`key_decision_kinds`); after deadline, default move (65.4).
  ⚠️ ASSUMPTION: list of key decision kinds (strategy card pick, primary steps, vote, hit assignment).
- Pace "for the eye": `move_delay_s` = 1 s pause before moving (admin fast mode: 0 — toggle to be added).
- Undo: the bot never undoes. When state changes during computation or pause (human move, Undo), the result
  is discarded and the bot recomputes. Rejected move (403/422) → next candidate from the decision.
- Absent human takeover by bot (RULES 44.5): at the end of bot work.
- Server: `uv run python -m src.api` runs bots; `--no-bots` disables them (manual control/God-Mode).


### 65.8 Random bot and B5 move variants (user decision 2026-11-18: "all random, to test things")
- The `random` algorithm (`engine/compute`) shuffles ALL `legal_actions` candidates (seed from request);
  assigned in `engine_config.json` to every difficulty level for testing (`first` = passive bot).
- ⚠️ ASSUMPTION: generator variants (`engine/legal_tactical.py`) are intentionally simple — the first candidate is
  always the safe move (end step / pass / decline), followed by:
  - activating a system that own ships can reach, or containing own units;
  - moving the entire movable fleet from a source, without cargo or with cargo up to full capacity (space,
    then own planets of the source system);
  - producing a single item (1 unit; fighters/infantry in a pair), automatic payment;
  - combat: attacker drives rolls, retreat: declare / keep fighting, retreat target = every legal system;
  - Space Cannon: pass or fire at every legal target; casualties as in 65.4 (Sustain Damage or without);
  - invasion: bombard one planet with all units, commit all forces to one planet,
    remove Custodians with all ready planets, defense: pass or fire;
  - exploration: every planet/deck, every available card option;
  - ACTION action cards with an engine effect: every option of the first form choice, the rest minimal;
  - researching technology with Technology card (primary: free and second for 6, secondary for 4): decline or
    every technology with status "available" (without specialty/relic prerequisite skips), payment
    with planets from most valuable, remainder in TG; when the player cannot afford it — only decline / pass
    (`engine/legal.research_payloads`).
- The bot does not use "may" abilities inside these steps (Gravity Drive, Plasma Scoring, extra AFB dice)
  nor reaction cards (bot reaction windows are passed by the engine).
- Random faction (setup, creator): fully implemented factions first (`core/faction_support`), then
  remaining playable factions.
